

| |抽象|建模|
|---|---|---|
|回答的问题|保留**什么**，在概念上它**是什么**|在 Rocq 里**怎么表示**|
|语言|自然语言 + 数学（集合、函数、整数）|Rocq 代码|
|例子|"余额是一个整数，没有上下界"|用 `Z` 而不是 `nat`|
|和工具的关系|换一个工具，这部分不变|换一个工具，这部分要重写|
分开的好处是：**编码方式本身也会引入假设**，分开写才能看出来。举个典型的坑：

> 如果用 Rocq 的 `nat` 表示余额，**余额从类型上就不可能为负**，而且 `nat` 的减法是截断的：`3 - 5 = 0`。这样一来"余额非负"不用证明就自动成立，但这是编码造成的，不是系统本身的性质。

## 更精确的抽象

| 项目       | 抽象结果                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| **实体**   | 账户：一个有限且固定的集合，只需要能区分两个账户是否相同                                                   |
| **属性**   | 每个账户有一个余额，取值为**整数，没有上下界**                                                      |
| **状态**   | 所有账户余额的整体，即一个"账户 → 整数"的映射                                                      |
| **初始状态** | 任意一组初始余额，前提是每个都 ≥ 0                                                            |
| **操作**   | 转账(a, b, n)：当 **n > 0** 且 a 的余额 ≥ n 时生效，a 减 n、b 加 n；否则状态不变。**a = b 时**，生效后余额不变 |
| **环境**   | 除转账外没有任何东西能改变余额                                                                |
| **删除**   | 用户界面、数据库、日志、手续费、管理员调账（记下：假设这些不影响总额）                                            |
| **替换**   | 64 位整数 → 无界整数（假设不溢出）；转账 → 原子操作，顺序执行（假设无并发交错）                                   |

（账户集合有限、n > 0、a = b 怎么处理）都是**写得精确以后才会冒出来的问题**：
- **账户有限**：规约要说"总额"，就得对所有账户求和，账户集合如果是无限的，"总额"就没有定义。这是**规约反过来要求抽象**更精确。
- **n > 0**：如果允许 n 为负，"从 a 转 -100 给 b"就等于从 b 偷 100 给 a，而"a 的余额 ≥ n"这个检查会被轻松绕过。
- **a = b**：自己转给自己会不会出问题，要事先说清楚。

## 建模（Rocq 编码）

```coq
Require Import ZArith List.
Open Scope Z_scope.

Section Bank.

  (* 账户：抽象类型，只要求能判断两个账户是否相同 *)
  Variable Account : Type.
  Variable account_eq_dec : forall a b : Account, {a = b} + {a <> b}.

  (* 账户集合有限且固定：所有账户列在一个无重复的列表里 *)
  Variable accounts : list Account.
  Hypothesis accounts_nodup : NoDup accounts.
  Hypothesis accounts_complete : forall a, In a accounts.

  (* 状态：每个账户的余额；用 Z（整数）而不是 nat *)
  Definition State := Account -> Z.

  (* 初始状态：所有余额非负 *)
  Definition Init (s : State) : Prop := forall a, 0 <= s a.

  (* 辅助函数：修改某个账户的余额 *)
  Definition update (s : State) (x : Account) (v : Z) : State :=
    fun y => if account_eq_dec y x then v else s y.

  (* 迁移：转账 *)
  Definition transfer (s : State) (a b : Account) (n : Z) : State :=
    if (0 <? n) && (n <=? s a) then
      let s1 := update s a (s a - n) in   (* 先从 a 扣款 *)
      update s1 b (s1 b + n)              (* 再基于 s1 给 b 入账 *)
    else s.

End Bank.
```

**编码选择及理由**：

|概念|Rocq 编码|为什么这样选|
|---|---|---|
|账户|`Variable Account : Type` + 可判定相等|不关心账户的具体内容，只需要能区分|
|账户集合有限|`accounts` 列表 + `NoDup` + 完备性|为了能对所有账户求和|
|余额|`Z`|避免 `nat` 掩盖负数和截断减法|
|状态|函数 `Account -> Z`|直接对应"账户 → 余额"的映射|
|初始状态|谓词 `Init`|允许任意满足条件的初始余额，而不是某一组具体数值|
|迁移|函数 `transfer`|转账是确定性的；如果有并发，就要改用 `Inductive` 关系|
|假设|`Section` 里的 `Variable` / `Hypothesis`|不用全局 `Axiom`，避免污染整个开发|

### 一个很能说明问题的细节
注意 `transfer` 里的 `s1`。如果写成：

```coq
update (update s a (s a - n)) b (s b + n)   (* 错误版本 *)
```

当 a = b 时，第二次更新用的是**原状态**的 `s b`，结果 a 的余额变成 `s a + n`：**凭空多出了 n 元。** 这正是之前提到的"自己转给自己"的 bug。

抽象里写一句"a 减 n、b 加 n"，看起来没有歧义；**到了编码时才必须决定"先扣再加时用的是哪个状态"**，bug 也就在这里暴露出来。这也说明抽象和建模虽然分开写，实际上是**来回迭代**的：建模时发现的问题，要回到抽象里补上（比如加上"a = b 时余额不变"这一条）。
