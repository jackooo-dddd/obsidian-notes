## 流程
1. 抽象：为了要证明的性质，决定保留、删除、替换什么。
    - 比如说用户有银行账户，里面有余额，我们会把这个银行账户，抽象成 Rocq 里面一个 Record，里面的余额即是一个 `Account → Int` 这样的关系。"银行账户用一个只含余额的数学对象来表示"，是抽象；在 Rocq 里把它写成 `Record` 或 `Account -> Z`，是建模。
2. 建模：把保留下来的东西写成 Lean/Rocq 里的代码。
    - 如果性质在任意次操作后都要满足，就建成状态机：写清楚状态、初始状态、迁移。例：银行转账系统，无论执行多少次转账，总额始终不变。
    - 如果性质只涉及输入输出，就用函数、数据类型或关系建模，不需要状态机。例：验证排序算法，只关心输出有序、并且是输入的一个排列，不关心中间过程。
3. 规约：把我们希望系统满足的性质写成模型的命题。
    - 规约从需求和意图出发，要确保它表达的正是我们一开始想说明的性质。这一点无法证明。
    - 某一性质的证明通过后，结论是：**在抽象和建模之下，并且在前提成立时**，模型具有该性质。
    - 常见的性质类型：
        - 不变式：每个可达状态都满足。
        - 前后置条件：输入满足前提时，输出满足要求。例：余额足够时，`transfer a b n` 之后 a 少了 n、b 多了 n，其他账户不变。
        - 精化：实现的行为与一个更简单的抽象规约一致。例：并发执行的转账，效果等同于按某种顺序逐笔执行。
4. 证明：引理（单步性质、辅助事实）→ 主定理（通常靠归纳）→ 推论（特殊情况）。

## 例子：银行转账系统

### 1. 抽象：只想清楚"是什么"，不涉及具体语言
- 保留什么
    - 账户：只需要能分辨两个账户是不是同一个，户名、账号等信息都不需要
    - 余额：每个账户一个整数
    - 转账：从账户 a 转 n 元到账户 b
- 转账（`transfer a b n`）的规则
    - 金额 n 大于 0，且 a 的余额够，转账才生效：a 减少 n，b 增加 n；否则什么都不变
    - 自己转给自己时，余额不变
- 删掉什么（记下假设：这些都不会影响总金额）：用户界面、数据库、日志、手续费
- 假设了什么
    - 余额不会溢出
    - 转账不会转到一半中断，也没有多笔转账同时进行
    - 除了转账，没有别的东西能改变余额

### 2. 建模：把抽象的描述写成 Rocq 代码

| 要表示的东西 | Rocq 里怎么写 | 说明 |
| --- | --- | --- |
| 账户 | 声明一种叫做 `Account` 的类型 `Parameter Account : Type.` | 不关心账户里有什么 |
| 余额 | 整数类型 `Z` | 不用自然数 `nat`：`nat` 没有负数，减法还会把 3 − 5 算成 0，会把透支的问题藏起来 |
| 状态 | 函数：给一个账户，返回它的余额 | |
| 初始状态 | 条件："所有账户余额 ≥ 0" | 任何满足条件的初始余额都可以 |
| 转账 | 函数 `transfer` | 先从 a 扣款，再在扣款后的结果上给 b 入账 |

建模完后，用几个具体的例子，检查我们在 Rocq 中定义的 `transfer` 函数，是否符合"转账"的预期。例如正常转账：a 少 n，b 多 n；余额不够：什么都不变。

### 3. 规约
从需求出发写命题：对任意可达状态，所有账户余额之和 = 初始总额，并且每个账户余额 ≥ 0。

## 建模这一步产生的假设

| 建模要素 | 背后的假设 |
| --- | --- |
| 余额表达为 `Account → Int` | 余额没有上限，不会溢出；账户集合是固定的，没有开户、销户 |
| 初始状态：给定的初始余额 | 系统启动时所有余额都是确定、已知的 |
| `transfer a b n` | ① 扣款和入账同时完成，不会只完成一半；② 转账顺序执行，没有转账交错；③ 余额不足时什么都不做；④ 真实代码的逻辑确实和这个函数一致 |
| 只有 `transfer` 这一种迁移 | 环境中没有其他东西能改变余额 |

### 转账系统模型 · 假设清单
```text
抽象：
  A1. 不考虑手续费、管理员调账、开户赠送等会改变总额的功能
  A2. 余额为无界整数，不考虑溢出
建模：
  M1. 账户集合固定，不开户、不销户
  M2. 转账是原子操作，不会只执行一半
  M3. 转账顺序执行，无并发
  M4. 余额不足时转账不生效
  M5. 除转账外，没有任何操作能改变余额
规约（已写入定理前提）：
  S1. 初始时所有账户余额 ≥ 0
```

## 假设的检验
**"模型符合真实系统"这件事本身无法被证明，只能被检验。** 形式化验证里面可以被证明的性质，是要在模型建立之后才开始有的。所以在建模之前，可以有大量的假设。

假设无法被证明，但可以被检验。每检验一条，对"模型忠实于真实系统"的信心就多一分。检验能发现假设不成立，但不能保证假设一定成立。

### 假设清单里的每一条，都可以找到对应的检验方式
| 假设 | 怎样在代码层面检验 |
| --- | --- |
| A1. 没有会改变总额的其他功能 | 在代码里搜索所有写入余额字段的地方，确认只有转账 |
| A2. 不考虑溢出 | 查看余额的类型和业务上限，确认真实金额达不到溢出范围 |
| M2. 转账是原子的 | 检查扣款和入账是否在同一个数据库事务里 |
| M3. 无并发 | 检查是否加了锁，或者是否运行在串行队列里 |
| M4. 余额不足时不生效 | 写测试：余额不足时发起转账，确认两个账户的余额都没变 |
| M5. 只有转账能改变余额 | 与 A1 相同，搜索所有写入点，并检查数据库权限 |

### 如何把模糊的抽象变得容易理解
"账户用一个只含余额的对象表示"非常难进行检验。这个抽象并不是在说真实的账户只有余额。真实账户还有户名、账号、密码等。但是我们可以说，因为我们只是想说明"总金额守恒"这个性质，对于这个性质，账户的其他属性不会影响余额怎么变化。这个抽象真正的意思是：

> 对于"总金额守恒"这个性质，账户的其他属性不会影响余额怎么变化。

这样一换，它就从一个模糊的哲学问题，变成了可以逐条核对的具体问题：

| 账户的其他属性 | 会影响余额的变化吗？ | 怎么检验 |
| --- | --- | --- |
| 户名、密码 | 不会 | 查代码：转账逻辑读不读这些字段 |
| 交易历史 | 不会（只是记录） | 查代码：历史只写入，不参与余额计算 |
| 冻结状态 | 会：冻结账户不能转出 | 查代码：转账前是否检查冻结标记 |
| 账户类型 | 可能会：信用账户允许余额为负 | 查代码 / 查业务规则 |

### 判断抽象好坏的核心标准：模型不能漏掉真实的行为
真实系统能做、模型里却做不到的行为。比如信用账户允许透支，模型里却没有这种情况。那么模型证明了"余额永远非负"，真实系统却可以是负数。
