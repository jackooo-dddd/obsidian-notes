**Rocq 里的 `l` 是一个全局 level：所有用到 `id` 的地方共用这同一个 `l`，但它没有具体的数值，只受约束表 C 限制。翻译到 Lean 后，它变成了可以随意取值的参数 `u_l`。这样翻译还对吗？**
- 对。Lean 检查的比 Rocq 更多：每个满足 C 的取值，都对应 Lean 那一族中的一个实例。前提是约束表一致（`Consistent C`）。
#### 1. 两边检查的东西不一样

| |声明|检查了什么|
|---|---|---|
|Rocq|`id`，使用全局 level `l`|在约束 C 下检查。`l` 没有具体数值，结论对**所有满足 C 的取值**都成立|
|Lean|`id.{u_l}`|对 `u_l` 的**所有取值**都成立，相当于一整族声明：`id.{0}`、`id.{1}`、`id.{2}`……|

所有取值包含了满足 C 的那些取值，所以 Lean 的 `id.{u_l}` 比 Rocq 的 `id` **更一般**。
#### 2. 取 `σ := ρ` 就能恢复原声明
- **任取**一个满足约束表 C 的赋值 ρ。
- 在 Lean 里让参数取同样的值：`σ(u_l) = ρ(l)`。
- 由核心引理 `I_eval`，在这个 σ 下，翻译后每个 Sort 的值，都等于 Rocq 原来的 Sort 在 ρ 下的值。

所以 Rocq 在 ρ 下的 `id`，就是 Lean 那一族中 `id.{ρ(l)}` 这个成员。ρ 是任取的，所以每个满足 C 的 ρ 都能这样对应上。

打个比方：Rocq 证明了"对**所有满足条件的** x，这件事成立"；Lean 证明了"对**所有** x，这件事都成立"。把 Lean 的结论限制到满足条件的 x 上，就回到了 Rocq 的结论。一般化没有改变原来的意思，只是说得更多。
#### 3. 为什么需要 `Consistent C`
- 如果 C 自相矛盾（比如同时有 `l < m` 和 `m < l`），就没有任何 ρ 满足 C。这时"对所有满足 C 的 ρ 成立"是一句空话，什么都能推出来，上面的对应关系也就没有意义了。
- `Consistent C` 保证至少有一个 ρ 满足 C。Rocq 内部会检查约束一致；但模型里的 C 经过了导出和翻译，它是否一致需要另外确认（见第 6 节）。
#### 4. 代价
Lean 要求"对所有取值都正确"，这比 Rocq 的"对满足 C 的取值正确"更强，所以一般化有时**做不到**。

例子：`Definition T : Type@{m} := Type@{l}` 依赖约束 `l < m`。翻译后，并不是对所有 `u_l`、`u_m` 都成立，Lean 会拒绝。这时项目要么报告拒绝，要么用 R2F-c 把约束写进 level 表达式：把 `u_m` 解释成 `max(u_m, u_l+1)`。这样处理后，取 `σ := ρ` 仍然能恢复原声明：ρ 满足 `l < m`，所以 `max(ρ(m), ρ(l)+1) = ρ(m)`。

所以结论是：**只要 Lean 接受了一般化后的声明，对每个满足 C 的 ρ，取 `σ := ρ` 都能恢复原声明；但不是每条 Rocq 声明都能直接一般化。**
