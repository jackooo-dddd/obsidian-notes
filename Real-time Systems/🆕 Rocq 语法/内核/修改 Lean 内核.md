修改内核能消除相当一部分 universe 规则，但**收益最大的那部分，恰好要求风险最高的改动**。下面按"改什么、能解决什么、风险多大"分三档，用项目里各条规则实际用到的根声明数来估计影响面。

说明：下面的数字是"用到这条规则的根声明数"，同一个声明可能用到多条规则，所以不能相加；而且"用到"不等于"改了内核就完全不需要"，只表示影响的范围。另外，2180 个根声明里有 1230 个最终没有用到任何特殊的 universe 处理，这部分不受影响。
## 第一档：Type 层之间的累积性 —— 风险较低，收益中等
**改什么**：允许 `Sort (u+1) ≤ Sort (v+1)`（u ≤ v），以及函数类型的返回类型可以变大。也就是 Rocq 的累积性，但**不包括 Prop**。

**为什么风险较低**：这是研究得很充分的类型论（Luo 的扩展构造演算，Rocq 一直在用），Agda 也提供了可选的累积性开关。不涉及 Lean 的 Prop 和证明无关性。

**能解决的问题**：

|问题|项目里的处理|规模|
|---|---|---|
|一个源层级被多个参数共用，Lean 会把它们强行绑成同一层（`list_R` 的例子）|R-SPLIT，复制层级|`level_copies` 66|
|Type 到更高 Type 的显式提升|类型提升转换|`type_lift_coercions` 36|
|引用时必须给出**正好相等**的层级，不能抬高|R3"不能抬高"、R2B 精确求解证明里的层级|几乎每个带参数的声明都受影响，但多数情况下 Lean 能自动解出|

有了累积性，引用时只要"不低于"即可，不必正好相等，R3 和 R2B 会大幅简化。
## 第二档：带约束的 universe 参数 —— 风险较低到中等，收益中等
**改什么**：允许声明带层级约束，例如 `def f.{u v | u < v}`，内核检查约束是否自洽，并在实例化时检查约束。Rocq 的 universe 多态早就支持这一点。

**能解决的问题**：

|问题|项目里的处理|规模|
|---|---|---|
|源声明依赖自己层级之间的严格关系（`ub < uc`），Lean 的独立参数无法表达|R2 直接报告拒绝；部分靠复制层级绕过|计入上面的 66 个中|
|Rocq 带约束的多态声明，Lean 只能把约束"解释"成 `max`|R6-I|`poly_level_interp` 26；接口中出现 `max`/`imax` 的有 227 个|

第一档和第二档合起来，基本相当于把 Lean 的 universe 系统改成 Rocq 那样：可以抬高，可以写约束。这样能去掉大部分"层级结构"上的绕行规则，接口也会更好读。
## 第三档：Prop ≤ Type 累积性 —— 风险高，收益最大
**改什么**：允许把命题当作 Type 使用。

**为什么收益最大**：项目里用得最多的几类 universe 处理，根源都是"Rocq 允许 Prop 当 Type 用"：

|问题|项目里的处理|规模|
|---|---|---|
|Type 参数在 Rocq 里可以接收 Prop 值的函数族（MathComp 的 `eq_bigr` 调用 `big_rec2`）|R8：把这类层级翻成 `Sort u`，允许 u = 0|`admitting_levels` **598**|
|`Prop ≤ Set`：`well_founded_induction` 要求返回 Set 的函数族，却收到返回 Prop 的|把这些常量按定义展开后再翻译|`delta_inlined` **156**|
|命题被直接当作 Type 用|插入 `PULift`|49 个根声明|
|`Prop : Type(1)` 和 `Prop : Sort 1` 差一层|专门的层级规则|少量|
|template 归纳类型在 Prop 上实例化|单独处理或拒绝|少量|

**为什么风险高**：上一轮说过，Lean 的 Prop 有**定义上的证明无关性**，在这一点上相当于 Rocq 的 SProp。而 Rocq 手册明确说 SProp 不参与累积性。把 Lean 的 Prop 加入累积性，正好落在 Rocq 刻意避开的组合上，需要新的一致性和可判定性论证，这是一个研究问题。
## 改内核也解决不了的

|问题|原因|
|---|---|
|**SProp 和 sort 品质多态**（Rocq 9 的 SProp/Prop/Type 三选一，项目里生成 3ⁿ 个分支）|要给 Lean 增加一个新的 sort 和品质变量，消去规则也随品质变化，改动规模远大于以上三档|
|**Rocq 全局层级的语义**|即使加了约束，Rocq 的层级是整个库共享的，Lean 的是每个声明私有的。翻译仍然要把全局层级映射成参数，规则 R0、R3 的核心逻辑仍然需要，只是会简化|
|**可读性**|参数多、名字是机械生成的（`u_Corelib_…`），这些不是内核问题|
|**`Case`/`Fix` 的改写**|这和 universe 无关，改 universe 规则帮不上|

## 代价：三档都要付出

|代价|说明|
|---|---|
|元理论论证|第一、二档有现成理论可以参考；第三档需要新的研究|
|前端|Lean 的合一、universe 推断都假设"严格相等、无约束"，需要改成能处理"≤"约束，工作量可能比内核本身还大|
|生态|翻译结果只在改过的内核里成立；标准 Lean、Mathlib 用户和外部检查器都不接受|
|信任|项目"由标准 Lean 内核检查"这一核心保证不再成立|

## 结论

|改动|风险|能去掉的绕行规则|规模|
|---|---|---|---|
|Type 层累积性|低|R-SPLIT、Type 提升，并简化 R3、R2B|约百个根声明，外加普遍的简化|
|universe 约束|低到中|R6-I 的 `max` 解释、严格关系的拒绝|几十个根声明，外加 227 个接口变得更好读|
|Prop ≤ Type 累积性|**高**|R8、Set 函数族的展开、`PULift`|**数百个根声明**，最大的一块|
|SProp / 品质多态|很高|品质分支|少量，但改动很大|

一句话总结：**第一、二档相对安全，主要收益是让层级结构更简单、接口更好读；数量上最大的一块（R8 的 598 个、展开的 156 个、`PULift` 的 49 个）都源于"Prop 当 Type 用"，必须做风险最高的第三档才能消除。**

所以对这个项目，比较现实的方向是：
- **保持标准内核**，继续用现有规则；
- **如果要做研究**，可以在 fork 里先做第一、二档，作为一个独立的实验。第三档需要先有元理论上的论证，才值得动手。
