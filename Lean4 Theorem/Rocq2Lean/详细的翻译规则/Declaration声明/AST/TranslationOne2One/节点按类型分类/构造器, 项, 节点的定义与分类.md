## 构造器、项、节点
**一句话：** 构造器是「项可以长成哪几种样子」；项是用构造器拼出来的一个具体的东西；节点是树里一个具体的位置，每个节点都属于某一种构造器。

| 概念 | 是什么 | 例子 |
|---|---|---|
| 构造器 | 节点的种类。整个系统里只有固定的几种：IR 里 17 种，Lean 的 `Expr` 里十几种 | `Rel`、`Const`、`Prod`、`Lambda`、`App`…… |
| 项 | 用构造器拼出来的一个具体的东西 | `Prod(n, nat, Prop)`，或者 `lt` 的整棵值树 |
| 节点 | 树里一个具体的位置，属于某一种构造器 | `lt` 值树里的某一个 `app` |

> [!tip] 类比
> `nat` 是类型，`O`、`S` 是构造器，`S (S O)` 是一个具体的值。同理，`Term` 是「项」这个类型，`Prod`、`App` 是构造器，`Prod(n, nat, Prop)` 是一个具体的项。
### 代码里的定义
这和代码里的定义完全一致。三处都是一个数据类型（「项」），下面列出它的若干构造器：

| | 数据类型（项） | 构造器 |
|---|---|---|
| Rocq 内核 | `kind_of_term`（`kernel/constr.mli`） | `Rel`、`Var`、`Sort`、`Prod`、`Lambda`、`App`…… |
| 项目 IR | `IR.Term`（`IR.lean`） | `rel`、`prod`、`lam`、`app`、`const`……共 17 个 |
| Lean 内核 | `Expr`（`Expr.lean`） | `bvar`、`sort`、`const`、`app`、`lam`、`forallE`…… |
### 在树上看：节点和项
以 `lt` 的值树为例：
```text
源树 S                                   目标树 T

lam n                  ── 节点 T02 ──►   lam n
├─ ind nat             ── 叶子 T03 ──►   ├─ const Rocq.…nat
└─ lam m               ── 节点 T02 ──►   └─ lam m
   ├─ ind nat          ── 叶子 T03 ──►      ├─ const Rocq.…nat
   └─ app              ── 节点 T02 ──►      └─ app
      ├─ ind le        ── 叶子 T03 ──►         ├─ const Rocq.…Peano.le
      ├─ app           ── 节点 T02 ──►         ├─ app
      │  ├─ construct nat 1 (S) ─ T03 ►        │  ├─ const Rocq.…nat.S
      │  └─ rel 1 (n)  ── 叶子 T01 ──►         │  └─ bvar 1 (n)
      └─ rel 0 (m)     ── 叶子 T01 ──►         └─ bvar 0 (m)
```
**每一行是一个节点；一个节点连同它下面缩进的所有行，是一个完整的项。**

- 叶子：下面没有东西，所以它自己这一行就是一个完整的项，比如 `ind nat`、`rel 1`。
- 组合节点：那一行只写了构造器，外加它自带的少量信息（例如 `lam n` 里的变量名 n），组成部分在下面的子节点里。把这一行和下面所有行合起来，才是完整的项：
```text
lam m                      ← 这一行 + 下面所有行
├─ ind nat                    = fun m : nat => le (S n) m
└─ app ...
```
所以整棵树的根 `lam n` 加上它下面的全部内容，就是 `lt` 的整个值 `fun n m => le (S n) m`。

> [!note] 子项语法上完整，但可能要靠外层的上下文才有意义
> - `rel 1` 是一个完整的项，但它指的是「往外数第 1 个变量」，单独拿出来不知道是谁；
> - 只有放在 `lam n`、`lam m` 下面，内核的上下文里有了 n 和 m，才能查到它的类型是 nat。
>
> 这就是内核处理组合节点时要「把 `x : T` 加入上下文」的原因：子项需要外层提供的变量才能检查。

## 内核怎么处理每种节点
内核检查一个项时，看它最外层节点的构造器，按该构造器的规则处理；子项递归处理。总览：

| 分类 | Rocq AST 节点 | Kernel 如何处理 |
|---|---|---|
| 叶子 / 引用 | `Rel`、`Var` | 从局部上下文获取变量类型 |
| 叶子 / 引用 | `Const`、`Ind`、`Construct` | 从全局环境获取声明的类型，并处理 Universe 实例 |
| 叶子 / Sort | `Sort` | 根据 Universe 规则确定其类型 |
| 复合节点 | `Prod` | 检查输入类型、输出类型，计算整个 Π 类型所在的 Sort |
| 复合节点 | `Lambda` | 检查参数类型和函数体，得到函数的 Π 类型 |
| 复合节点 | `App` | 检查函数和实参的类型，进行类型兼容性检查及结果类型替换 |
| 复合节点 | `LetIn` | 检查局部定义及其使用 |
| 特殊复合节点 | `Case`、`Fix`、`CoFix` | 检查消去、递归等规则及其限制 |

下面逐个说明，并用 `lt` 中的具体节点举例。叶子的进一步分类见 [[叶子节点的分类]]。
### 一、叶子 / 引用：`Rel`、`Var`
内核做的事是在上下文里查变量，取出它的类型：

- `Rel n`：按编号往外数第 n 个已引入的变量。Rocq 取类型时还要调整编号（`lift`），因为这个类型是在外层写的。
- `Var`：按名字查 section 变量。
- 报错情况：编号超出范围，或名字找不到。

Lean 进入 binder 时先把变量换成带名字的局部变量（`fvar`），再用 `infer_fvar` 去查。方式不同，效果相同。

`lt` 里：在 `le (S n) m` 中，`n` 是 `Rel 1`，查到类型 nat；`m` 是 `Rel 0`，查到类型 nat。
### 二、叶子 / 引用：`Const`、`Ind`、`Construct`
内核做的事是在全局环境里查声明，取出类型，并代入 Universe 实例：

1. 声明必须存在；
2. 取出它的类型：`Const` 取声明的类型，`Ind` 取第几个归纳类型的类型，`Construct` 取第几个构造子的类型；
3. 把引用时给的 Universe 实例代入类型，并检查这个实例满足声明的 Universe 约束。

Lean 没有 `Ind`、`Construct`，都用 `const` 表示，走同一个函数 `infer_constant`。它检查 Universe 参数个数要对上、每个 Level 合法，并且不能引用 `unsafe` 或 `partial` 的声明。

`lt` 里：`le` 查到类型 `nat → nat → Prop`；`S` 查到类型 `nat → nat`。
### 三、叶子 / Sort：`Sort`
内核做的事是按 Universe 规则直接给出类型，不查任何地方：

| Rocq | 类型 |
|---|---|
| `Prop`、`SProp`、`Set` | `Type(1)` |
| `Type(u)` | `Type(u+1)` |

Lean 是 `Sort u` 的类型为 `Sort (u+1)`，并检查 Level 合法。Rocq 还会检查当前环境是否允许使用 SProp。
### 四、复合节点：`Prod`
对 `∀x : T, B`，内核分四步：

1. 推出 T 的类型，必须是一个 Sort，否则报「不是类型」；
2. 把 `x : T` 加入上下文；
3. 推出 B 的类型，也必须是一个 Sort；
4. 由 T 和 B 所在的层算出整个 Π 所在的层：B 是命题则结果是命题，否则取较高的层。Rocq 用 `sort_of_product`，Lean 用 `imax`。

`lt` 的类型 `∀ (n m : nat), Prop`：nat 是类型，Prop 是类型，所以整体是一个类型。
### 五、复合节点：`Lambda`
对 `fun x : T => b`，内核分四步：

1. T 必须是类型；
2. 把 `x : T` 加入上下文；
3. 推出 body b 的类型 B；
4. 结果是 Π 类型 `∀x : T, B`。Rocq 用 `mkProd` 构造，Lean 用 `mk_pi` 构造。

`lt` 的值：body `le (S n) m` 推出 Prop，包上两层后得到 `∀ (n m : nat), Prop`。
### 六、复合节点：`App`
对 `f a`，内核分三步：

1. 推出 f 的类型，化简后必须是 Π 类型 `∀x : T, B`，否则报「不是函数」；
2. 推出 a 的类型，判断它是否符合 T，否则报「参数类型不匹配」；
3. 结果类型是 B 中的 x 换成 a。

两边有两处区别：

- 多个参数：Rocq 一个节点存多个参数，`type_of_apply` 逐个按 1–3 步处理；Lean 是嵌套的 app，每层处理一个参数。
- 「符合」的标准：Rocq 用 `conv_leq`，允许参数类型小一层；Lean 用 `is_def_eq`，要求相等。

`lt` 里：`S n` 推出 nat；`le (S n)` 推出 `nat → Prop`；再接上 `m`，推出 Prop。
### 七、复合节点：`LetIn`
对 `let x : T := v in b`，内核分五步：

1. T 必须是类型；
2. 推出 v 的类型，必须符合 T；
3. 把 `x : T := v` 加入上下文。和 Lambda 不同，这里的 x 带着值，之后判相等时可以把 x 展开成 v；
4. 推出 body b 的类型；
5. 结果是 b 的类型，其中的 x 用 v 代替。

Lean 的 `letE` 处理方式相同。
### 八、特殊复合节点：`Case`、`Fix`、`CoFix`
这三种只有 Rocq 内核里有，Lean 内核没有对应的节点。它们的规则比前面复杂，还附带限制。
#### `Case`（match）
1. 推出被匹配项的类型，必须是某个归纳类型（带上参数和索引）；
2. 检查返回类型（motive）合法；
3. 检查消去限制：比如对一个命题做 match，一般不能得到数据（Prop 不能随意消去到 Type，只有少数「单例」情况例外）；
4. 对每个构造子，检查对应分支的类型等于「返回类型在这个构造子上的取值」；
5. 结果类型是返回类型代入被匹配的项。
#### `Fix`（递归）
1. 每个递归函数声明的类型必须是类型；
2. 把这组递归函数本身加入上下文（因为 body 里会调用自己），检查每个 body 符合它声明的类型；
3. 守卫条件（guard condition）：每次递归调用，在指定的递减参数位置上，必须传入结构上更小的项，例如 `S p` 的 `p`。这一条保证递归会终止。
### 补充：被引用对象的正确性由谁保证
叶子里的引用节点（第一、二节）直接取类型，不再检查被引用的东西本身。它们的正确性由它进入环境或上下文的那一刻保证：

| 被引用的对象 | 它什么时候被检查过 | 由什么保证 |
|---|---|---|
| 全局声明（`nat`、`le`、`S`） | 它自己作为一条声明加入环境时，内核已经完整检查过（类型是类型、值符合类型） | 环境里只有通过检查的声明，所以查到的一定是合法的 |
| 局部变量（`n`、`m`） | 引入它的组合节点（外层 `fun n : nat`）在第 1 步检查过 `nat` 是类型 | 上下文里只有检查过的变量 |

所以，引用节点能「放心地」直接取类型，前提是之前的检查已经做完：

- 全局声明：靠外层归纳，按声明顺序，先检查、后引用；
- 局部变量：靠引入它的那个 Prod 或 Lambda。
