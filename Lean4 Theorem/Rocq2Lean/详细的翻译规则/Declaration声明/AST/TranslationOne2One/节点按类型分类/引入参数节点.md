为什么需要节点来引入参数：[[⚠️ Prod 和 Lambda 包装 以及为什么要有 Prod 和 Lam]]
## 先看这个仓库 IR 里每种 binder 的真实字段
字段名摘自 `translator/Rocq2Lean/IR.lean:48`：

| 节点 | 字段 | 引入几个变量 | 变量的类型从哪来 | 整个节点造出什么 |
|---|---|---|---|---|
| **Prod** | `(n, ty, body)` | 1 | 写在 `ty` 里 | 一个**类型**（函数类型） |
| **Lambda** | `(n, ty, body)` | 1 | 写在 `ty` 里 | 一个**值**（函数） |
| **LetIn** | `(n, val, ty, body)` | 1 | 写在 `ty` 里，**另外还带一个值 `val`** | **跟 body 一样**：body 是类型就造出类型，是值就造出值 |
| **Case 分支** | `(names[], body)` | 每个分支若干个 | **不存**，由构造子的签名推出来 | 跟分支 body 一样，可能是值，也可能是类型 |
| **Fix** | `defs[(n, ty, body, rarg)], idx` | 多个（互递归时每个函数一个） | 写在每个 `ty` 里 | 一个**值**（递归函数） |

`add` 导出的数据可以印证 Case 分支那一行：`S p` 分支只存了 `"ctx": [{"n": "p"}]`，有名字，但**没有类型**。kernel 知道 `S : nat -> nat`，所以 `p` 一定是 `nat`，没必要再存一份。

### "按造出来的是什么分类"只适用于 Prod 和 Lambda

这两个节点的字段完全一样，唯一的区别就是造出类型还是造出值。所以它们要靠"造出什么"来区分。

其他 binder 是按**机制**区分的：
- **LetIn**：作用是"给一个值起个局部名字"，不决定造出的是类型还是值。

```coq
let T := nat in T -> T       (* 整体是一个类型 *)
let x := 3 in S x            (* 整体是一个值 *)
```

- **Case**：作用是"按构造子分情况"。它造出来的可以是值，也可以是类型：

```coq
match b with true => nat | false => bool end    (* 每个分支都是类型 *)
```

- **Fix**：作用是"让函数在自己的函数体里能引用自己"。

## 真正统一的东西：上下文里的一条记录
不同 binder 的字段虽然各不相同，但它们做的事是一样的：往局部上下文里**压入记录**。记录本身的格式是统一的。仓库 IR 里就定义了这个格式（`IR.lean:74`）：

```lean
structure CtxDecl where
  name : AName
  body : Option Term   -- 有没有具体的值
  type : Term          -- 变量的类型
```

各种 binder 压入的记录：

| binder | 压入的记录 |
|---|---|
| Prod / Lambda | `{ name, body = none, type = ty }`，只知道类型，值未知 |
| LetIn | `{ name, body = some val, type = ty }`，类型和值都知道 |
| Case 分支 | 每个构造子参数一条 `{ name, none, 从构造子推出的类型 }` |
| Fix | 每个递归函数一条 `{ name, none, ty }` |



## 这些节点不只是为了引入变量。

引入变量只是这些节点的共同点。kernel 之所以把它们分成不同的节点，是因为每个节点各自带着一套**不同的规则**，而 kernel 要靠这些规则完成两件工作：

### 1. 类型规则：这个项的类型是什么？

每个项都有类型，包括 Prod 和 Lambda 自己。每种节点的类型规则，说的是怎样从子项的类型算出整个节点的类型。以 `lt` 为例：

- body `Lambda(n, nat, Lambda(m, nat, le (S n) m))`，也就是 `fun (n m:nat) => S n <= m`，它的类型是 `Prod(n, nat, Prod(m, nat, Prop))`。规则是：把 `n`、`m` 加进上下文，算出 body 的类型 `Prop`，再在外面套上同样的两层 Prod。
- type `Prod(n, nat, Prod(m, nat, Prop))`，也就是 `forall (n m:nat), Prop`，它本身也是一个项，类型是 `Type`。规则是：看参数类型 `nat` 和返回类型 `Prop` 各在哪个 universe，按 universe 规则算出一个 Sort。

### 2. 计算规则：这个项能不能化简？化简成什么？
kernel 判断两个类型是否相等时，要先把它们算到底再比较。光有 Lambda 不会化简，要有 App 把实际的值填进来。以 `lt 2 5` 为例：

```
lt 2 5
→ (fun n m => S n <= m) 2 5      δ：把常量 lt 展开成它的 body
→ S 2 <= 5                       β：把 2 代入 n，5 代入 m
```

结果是命题 `3 <= 5`（它的类型是 `Prop`），算到这里就停了，因为 `le` 是归纳类型，不会再展开。所以，如果要证明 `lt 2 5`，只要给出一个 `3 <= 5` 的证明，kernel 把两边算到底，发现它们一样，就会接受。

## 每个节点各自的规则

| 节点 | 类型规则（特别的地方） | 计算规则 | 额外的检查 |
|---|---|---|---|
| **Prod** | 自己的类型是一个 Sort，要按 universe 规则算出来 | **没有**，类型本身不会被化简 | 无 |
| **Lambda** | 类型是一个 Prod | **β 归约**：`(fun x => t) a` 化简为 `t[x:=a]` | 无 |
| **LetIn** | 检查 body 时，**x 的值是已知的** | **ζ 归约**：把 x 替换成它的值 | 无 |
| **Case** | 用 return 谓词算出类型，每个分支的类型可以不一样 | **ι 归约**：匹配对象是构造子时，选出对应分支 | 分支要齐全；限制能否从 Prop 消去到 Type |
| **Fix** | 类型就是写在 `ty` 里的那个 | 只有当递归参数是构造子时，才展开一层 | **guard checker**：必须是结构递归 |

下面挑三个最能说明问题的例子。
## 例 1：Prod 和 Lambda 字段相同，但规则不同
Prod 的类型要按 universe 规则计算，其中一条特殊规则是 **Prop 的非直谓性**：只要返回类型是 Prop，整个 Prod 的类型就是 Prop，不管参数是什么。

```coq
nat -> nat                : Set     (* 普通情况 *)
forall n:nat, n <= n      : Prop    (* 返回 Prop，所以整体也是 Prop *)
forall P:Prop, P          : Prop    (* 甚至可以对所有命题做量化，结果仍然是 Prop *)
```

Lambda 根本不涉及这套规则，它的类型直接就是一个 Prod。反过来，Lambda 能参与 β 归约，Prod 不能。
## 例 2：LetIn 不等于"Lambda 加 App"
看起来 `let x := v in t` 可以写成 `(fun x => t) v`，但两者在类型检查时并不一样：

```coq
let T := Type in ... 换成更简单的例子：

let T := nat in (3 : T)              (* 通过：检查 body 时知道 T 就是 nat *)
(fun T : Set => (3 : T)) nat         (* 失败：在 Lambda 里面，T 是一个未知的 Set *)
```

原因在于 LetIn 压入上下文的记录是 `{T, body = some nat, type}`，值是已知的；而 Lambda 压入的是 `{T, body = none, type}`，值未知。上一轮提到的 `CtxDecl.body : Option Term`，区别就在这里。
## 例 3：Fix 不检查的话，逻辑就会出问题
如果 Fix 和 Lambda 是同一个节点、没有 guard checker，就可以写出：

```coq
fix f (n : nat) : False := f n
```

它的类型检查完全没有问题，返回类型确实是 `False`。然后 `f 0 : False`，这就相当于**证明了 False**，整个逻辑系统就崩溃了。

所以 Fix 必须是单独的节点：kernel 一看到它，就要额外运行终止性检查。计算规则也要单独限制，只有递归参数已经是构造子时才展开，否则判断类型相等时会无限展开下去。
## 为什么不合并成一个节点？
如果硬合并成一个节点，就得在里面加一个标签，告诉 kernel "这次按 Prod 的规则检查，那次按 Fix 的规则检查"。这其实就是把不同的节点换了个写法，规则并没有变少。

**节点的划分，本质上就是规则的划分。**
## Lean 的做法正好印证了这一点
Lean 的 `Expr` 里只有 `forallE`、`lam`、`letE`，**没有 Case 和 Fix 节点**。但"分情况"和"递归"这两种功能并没有消失，而是放进了一个**特殊的常量** `T.rec`（recursor）：
- 它的计算规则（ι 归约）挂在这个常量上，不在节点上。
- 它天生只支持结构递归，所以 Lean 不需要 guard checker。

所以两边需要的**规则**本质上是一样的，区别只在于是用节点来承载，还是用常量来承载。这也正是这个翻译器最核心的工作：把 Rocq 节点里的 Case/Fix 规则，改写成 Lean 里的 `nat.rec` 常量。
