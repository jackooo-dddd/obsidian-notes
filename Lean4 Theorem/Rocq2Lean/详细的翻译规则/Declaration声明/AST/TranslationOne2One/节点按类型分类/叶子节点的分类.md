叶子节点本身检查很少，它的作用主要是**告诉内核这里指的是谁**，类型再从被指向的地方取来。
- **Sort 不属于这一类**：它不指向任何地方，它本身就是类型论里的基本对象；
- **检查少，但不是没有**：引用全局声明时，内核还要核对 universe 实例。
## 一、两类叶子

|类型|节点|指向哪里|类型从哪来|
|---|---|---|---|
|**局部引用**|`Rel`、`Var`|当前上下文里已经引入的变量，比如外层 Prod 或 Lambda 引入的 x|引入这个变量时写明的类型|
|**全局引用**|`Const`、`Ind`、`Construct`|环境里已经定义好的声明，比如 `nat`、`le`、`S`|那个声明的类型，再代入 universe 实例|
|**Sort**|`Sort`|不指向任何地方|由固定规则直接给出，比如 `Prop` 的类型是 `Type(1)`|

## 二、内核具体检查什么
### 局部引用：`Rel` / `Var`
**Rocq：**

```ocaml
let type_of_relative env n =
  try
    env |> lookup_rel n |> RelDecl.get_type |> lift n   (* 按编号查到变量，取出它的类型 *)
  with Not_found ->
    error_unbound_rel env n                             (* 查不到：报错 *)
```

只做两件事：按编号在上下文里找到变量，取出它的类型。

最后的 `lift n` 是因为这个类型是在更外层写的，搬到当前位置时要把里面的变量编号整体调整一下。

**Lean：**

```cpp
case expr_kind::BVar:
    lean_unreachable();          // 类型检查时不会遇到 bvar

expr type_checker::infer_fvar(expr const & e) {
    if (optional<local_decl> decl = m_lctx.find_local_decl(e))
        return decl->get_type();                       // 在局部上下文里找到变量，取出类型
    else
        throw kernel_exception(env(), "unknown free variable");
}
```

Lean 内核进入 forall 或 lam 时，会先把 body 里的 `bvar` 换成一个带名字的局部变量（`fvar`），所以检查时遇到的是 `fvar`，不是 `bvar`。查找方式和 Rocq 一样：在局部上下文里找到它，取出类型。

**两边相同：** 局部引用只是"查上下文、取类型"。
### 全局引用：`Const` / `Ind` / `Construct`
**Rocq：**

```ocaml
let type_of_constant env (kn,_u as cst) =
  let () = check_constant env kn in           (* 1. 这个常量必须存在 *)
  let ty, cu = constant_type env cst in       (* 2. 取出它的类型，代入 universe 实例 *)
  let () = check_poly_constraints cu env in   (* 3. 这个实例要满足声明的 universe 约束 *)
    ty
```

`Ind` 和 `Construct` 的检查（`type_of_inductive`、`type_of_constructor`）结构相同：
1. 找到归纳类型的声明；
2. 取出第几个类型或第几个构造子的类型；
3. 检查 universe 约束。

**Lean：**

```cpp
expr type_checker::infer_constant(expr const & e, bool infer_only) {
    constant_info info = env().get(const_name(e));          // 1. 找到声明
    if (length(ps) != length(ls)) throw ...;                // universe 参数个数必须对上
    ...                                                     // 不能引用 unsafe / partial 声明
    for (level const & l : ls) check_level(l);              // 每个 universe 都要合法
    return instantiate_type_lparams(info, ls);              // 2. 取出类型，代入 universe
}
```

Lean 没有单独的 `Ind`、`Construct` 节点。归纳类型和构造子也都是 `const`，走的是同一个函数。

**两边相同：** 全局引用是"查环境、取类型、代入并核对 universe"。
### Sort
**Rocq：**

```ocaml
let type_of_sort = function
  | SProp | Prop | Set -> type1                          (* 这三个的类型都是 Type(1) *)
  | Type u | GSort (_, u) | VSort (_, u) -> type_of_type u  (* Type(u) 的类型是 Type(u+1) *)
```

另外还检查当前环境是否允许使用 SProp。

**Lean：**

```cpp
case expr_kind::Sort:
    if (!infer_only) check_level(sort_level(e));   // level 要合法
    r = mk_sort(mk_succ(sort_level(e)));           // Sort u 的类型是 Sort (u+1)
```

Sort 不查任何地方，类型由规则直接算出：上一层。
## 三、所以叶子的对应归结为"指向的东西对应"
叶子的类型不是由叶子自己决定的，而是由**它指向的东西**决定的。所以翻译时，叶子只需要保证一件事：**翻译后指向的东西，和原来指向的东西相对应。**

|叶子|要保证什么|由什么保证|
|---|---|---|
|局部引用|两边上下文里同一位置是同一个变量|外层每个 Prod、Lambda 都翻译成 forallE、lam，两边每次都引入同一个变量，编号一致|
|全局引用|翻译后的名字指向原声明翻译出来的那个声明；universe 实例换算正确|外层归纳：被引用的声明先翻译并通过检查；universe 按规则换算|
|Sort|层级按对照表换算|固定规则|

## 四、叶子虽然检查少，但会影响组合节点

**1. universe 实例是叶子里唯一有实质内容的部分。** 引用一个声明时，不只说"指向谁"，还要说"用哪一层的版本"。两边内核都会检查这个实例是否合法。翻译里关于 universe 的规则大多落在这一步。

**2. 指向的东西还决定了"能不能展开"。** 组合节点检查时，常常要比较两个类型是否相等。如果叶子指向一个透明定义，比较时可以把它展开成定义体再比；如果指向的是不展开的声明（比如用 `Qed` 结束的证明），就不能展开。所以翻译后指向的声明，可展开性也必须和原来一致：透明定义翻成 `def`，不展开的翻成 `theorem` 或 `opaque`。

**3. Sort 两边的规则差一层。** 从 Rocq 代码可以看到，`Prop` 的类型是 `Type(1)`，按对照表应该对应 Lean 的 `Sort 2`；但 Lean 里 `Prop`（即 `Sort 0`）的类型是 `Sort 1`。Rocq 里这不成问题，因为有累积性；Lean 没有，所以这是叶子规则里唯一不完全对上的地方，翻译器有专门的规则处理它。
## 叶子总结
- **局部引用**：查上下文，取类型。两边一样。
- **全局引用**：查环境，取类型，代入并核对 universe。两边一样，只是 Lean 把 `Ind`、`Construct` 也当作普通常量。
- **Sort**：不指向任何地方，类型直接取上一层。两边规则一样，只有 `Prop` 和 `Set` 所在的那一层需要特别处理。
