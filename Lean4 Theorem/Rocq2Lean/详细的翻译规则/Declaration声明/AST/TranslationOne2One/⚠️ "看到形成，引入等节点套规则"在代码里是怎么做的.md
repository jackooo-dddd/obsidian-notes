Rocq 和 Lean 的 kernel 在检查一个项时，看到 `Prod`/`forallE` 节点，就套用类型论里的 Π 形成规则：检查 A 是类型，把 `x:A` 加进上下文，检查 B 是类型，再按 universe 规则算出整个 Π 的 Sort。
- 规则写在 kernel 代码里：Rocq 是 `typeops.ml` 的 `Prod` 分支加 `sort_of_product`，Lean 是 `infer_pi` 加 `imax`。

kernel 的做法就是：**看到哪种节点，就套用对应的那一条规则**。看到 `Prod`/`forallE`，就执行 Π 形成规则；只不过规则不是写在纸上，而是写成了代码。
## "看到节点就套规则"在代码里是怎么做的
每种节点恰好对应一条规则，所以 kernel 只要看一眼节点种类，就知道该用哪条规则。代码里就是一个按节点种类分发的 `match`/`switch`：

```ocaml
(* Rocq：typeops.ml 的 execute *)
match kind cstr with
| Prod (name,c1,c2)   -> ... Π 形成规则
| Lambda (name,c1,c2) -> ... λ 引入规则
| App (f,args)        -> ... 应用规则
```

```cpp
// Lean：type_checker.cpp:350
case expr_kind::Lambda: r = infer_lambda(e, infer_only); break;
case expr_kind::Pi:     r = infer_pi(e, infer_only);     break;
case expr_kind::App:    r = infer_app(e, infer_only);    break;
```


# Prod（Π）

## 1. 用 `Πn:nat. nat` 实际走一遍代码

把纸上的三步和两边的代码逐行对照：

| 纸上的步骤 | Rocq（`Prod` 分支） | Lean（`infer_pi`） |
| --- | --- | --- |
| 1. A 是类型吗？ | `execute_is_type env nat`，得到 `Set` | `ensure_sort_core(infer_type_core(Nat))`，得到 `Sort 1` |
| 2. 假设 `n : nat`，B 是类型吗？ | `push_rel (n:nat)`，再 `execute_is_type env1 nat`，得到 `Set` | `mk_local_decl(n, Nat)`，再 `ensure_sort_core(...)`，得到 `Sort 1` |
| 3. 算出整个 Π 的 Sort | `sort_of_product Set Set`，得到 `Set` | `imax(1, 1) = 1`，得到 `Sort 1`（即 `Type`） |
| 结论 | `Πn:nat. nat : Set` | `Nat → Nat : Type` |

两边的结果"看起来"不一样，是因为 Rocq 有单独的 `Set`，而 Lean 里对应的就是 `Type`（即 `Sort 1`）。这也是翻译器把 `Set` 翻成 `Type` 的原因。

## 2. 算 Sort 时容易混淆的两个例子

### 例 1：`Πn:nat. n ≤ n`（自反的类型）

| 步骤 | Rocq | Lean |
| --- | --- | --- |
| 1 | `nat : Set` | `Nat : Sort 1` |
| 2 | `n ≤ n : Prop` | `n ≤ n : Sort 0` |
| 3 | B 的 Sort 是 Prop，满足 `is_impredicative_sort`，结果为 `Prop` | `imax(1, 0) = 0`，结果为 `Sort 0` = `Prop` |

### 例 2：`Πn:nat. Πm:nat. Prop`（`lt` 的类型）

| 步骤 | Rocq | Lean |
| --- | --- | --- |
| 1 | `nat : Set` | `Nat : Sort 1` |
| 2 | B 是 `Prop` **本身**，而 `Prop : Type` | `Prop : Sort 1` |
| 3 | B 的 Sort 是 `Type`，不是 Prop，所以取较大者，结果为 `Type` | `imax(1, 1) = 1`，结果为 `Type` |

要分清：第一个例子里，B（`n ≤ n`）**是一个命题**，它的类型是 Prop，所以整个 Π 是 Prop。第二个例子里，B **就是 `Prop` 这个 Sort 本身**，它的类型是 Type，所以整个 Π 是 Type。前面说 `lt` 的 type 的类型是 `Type`，原因就在这里。

# Lambda（λ）

下面用同样的方式走一遍 Lambda。先把两边的代码放出来，再逐行对照三个例子。

## 1. 两边的代码

**Rocq**（`typeops.ml:655`，`Lambda` 分支）：

```ocaml
| Lambda (name,c1,c2) ->                                   (* λx:A. t *)
  let s = execute_is_type tbl env c1 in                    (* ① A 是类型吗？ *)
  let () = check_assum_annot env s name (self c1) in       (*    顺便核对 binder 上的相关性标注 *)
  let env1 = push_rel (LocalAssum (name,self c1)) env in   (* ② 把 x:A 加进上下文 *)
  let c2t = execute tbl env1 c2 in                         (* ③ 算出函数体 t 的类型 B *)
  type_of_abstraction env name (self c1) c2t               (* ④ 返回 mkProd(x, A, B) *)
```

**Lean**（`type_checker.cpp:125`，`infer_lambda`）：

```cpp
while (is_lambda(e)) {                                       // 连续多层 λ 一次处理
    expr d = instantiate_rev(binding_domain(e), ...);
    if (!infer_only) ensure_sort_core(infer_type_core(d), d);  // ① A 是类型吗？
    expr fvar = m_lctx.mk_local_decl(..., binding_name(e), d, ...);  // ② 把 x:A 加进上下文
    fvars.push_back(fvar);
    e = binding_body(e);
}
expr r = infer_type_core(instantiate_rev(e, fvars...));     // ③ 算出函数体的类型 B
return m_lctx.mk_pi(fvars, r);                              // ④ 返回 Πx:A. B
```

## 2. 与 Prod 分支对比：只有第 ③④ 步不同

| 步骤 | Prod（Π 形成） | Lambda（λ 引入） |
| --- | --- | --- |
| ① | A 是类型吗？ | **相同** |
| ② | 把 `x:A` 加进上下文 | **相同** |
| ③ | `execute_is_type`：检查 B **是一个类型**，取出它的 Sort | `execute`：算出 t 的**类型**是什么，t 可以是任何值 |
| ④ | 用 universe 规则算出一个 **Sort** | 套一层 Π，返回一个 **Π 类型** |

Prod 分支的结果是 Sort，Lambda 分支的结果是 Π。这和"Π 造出类型，λ 造出值"完全对应。

## 3. 三个例子

### 例 1：加二 `λn:nat. S (S n)`

| 纸上的步骤 | Rocq | Lean |
| --- | --- | --- |
| ① A 是类型吗？ | `execute_is_type env nat`，得到 `Set` | `ensure_sort_core(infer_type_core(Nat))`，得到 `Sort 1` |
| ② 假设 `n : nat` | `push_rel (n:nat)`，此后 `Rel 0` 就是 n | `mk_local_decl(n, Nat)`，生成一个 fvar `n` |
| ③ 算出函数体的类型 | `execute env1 (S (S (Rel 0)))`，得到 `nat` | `infer_type_core(Nat.succ (Nat.succ n))`，得到 `Nat` |
| ④ 套上 Π | `mkProd(n, nat, nat)` | `mk_pi([n], Nat)` |
| 结论 | `λn:nat. S (S n) : Πn:nat. nat` | `fun n => n.succ.succ : Nat → Nat` |

第 ③ 步内部会**递归**检查函数体：

```text
execute env1 (S (S (Rel 0)))
  └ 这是 App，进入 App 分支：S 的类型是 nat → nat，参数是 S (Rel 0)
      └ 又是 App：S 的类型是 nat → nat，参数是 Rel 0
          └ 这是 Rel，到上下文里查第 0 个变量：n : nat   ✓
        所以 S (Rel 0) : nat   ✓
    所以 S (S (Rel 0)) : nat
```

Lambda 分支自己只管 λ 这一层，函数体里的每个节点交给各自的分支去检查。

### 例 2：自反 `λn:nat. le_n n`（依赖的情况）

| 纸上的步骤 | Rocq | Lean |
| --- | --- | --- |
| ① A 是类型吗？ | `nat : Set` | `Nat : Sort 1` |
| ② 假设 `n : nat` | `push_rel (n:nat)` | 生成 fvar `n` |
| ③ 算出函数体的类型 | `execute env1 (le_n (Rel 0))`，得到 `le (Rel 0) (Rel 0)` | `infer_type_core(le_n n)`，得到 `le n n`（`n` 是 fvar） |
| ④ 套上 Π | `mkProd(n, nat, le (Rel 0) (Rel 0))` | `mk_pi([n], le n n)` |
| 结论 | `Πn:nat. n ≤ n` | `∀ n, n ≤ n` |

这个例子能看清**依赖是怎么被记录下来的**。第 ③ 步算出的类型里含有变量 n，到第 ④ 步这个 n 要"挂到"新生成的 Π 上。两边的做法不同：

- **Rocq**：第 ③ 步是在 `push_rel` 之后的上下文里算的，`Rel 0` 指的正是 n。第 ④ 步 `mkProd` 用**同一个** binder 包起来，于是 `Rel 0` 自动变成指向这个 Π 的 n。de Bruijn 编号一个都不用改。
- **Lean**：第 ③ 步算出的 `le n n` 里，n 是一个 fvar（有名字的自由变量）。第 ④ 步 `mk_pi` 会把这个 fvar **抽象**回 bvar 0，让它指向新生成的 `forallE`。

### 例 3：`lt` 的函数体 `λn:nat. λm:nat. S n ≤ m`（两层 λ）

| 纸上的步骤 | Rocq | Lean |
| --- | --- | --- |
| 外层 ①② | `nat` 是类型；`push_rel (n:nat)` | 循环第 1 轮：`Nat` 是类型；生成 fvar `n` |
| 内层 | 函数体又是一个 Lambda，于是**递归**进入 Lambda 分支：`nat` 是类型；`push_rel (m:nat)` | 循环第 2 轮：`Nat` 是类型；生成 fvar `m` |
| ③ 算出最里面的类型 | `execute env2 (le (S (Rel 1)) (Rel 0))`，得到 `Prop` | `infer_type_core(le n.succ m)`，得到 `Prop` |
| ④ 套上 Π | 内层返回 `mkProd(m, nat, Prop)`，外层再套一层，得到 `mkProd(n, nat, mkProd(m, nat, Prop))` | 一次性 `mk_pi([n, m], Prop)` |
| 结论 | `Πn:nat. Πm:nat. Prop` | `Nat → Nat → Prop` |

这里能看到两边实现风格的差异：**Rocq 一层 λ 进一次分支，靠递归处理多层；Lean 用一个 `while` 循环一次处理完连续的 λ**。结果完全一样。

## 4. 三个值得注意的细节

### 1. 生成的 Π 不会再检查一遍

第 ④ 步造出的 Π 类型，kernel **不会**再拿去跑一遍 Π 形成规则。Rocq 源码的注释（`typeops.ml:187`）说明了原因：在 CIC 里，只要 A 是类型、B 是类型，这个积就一定合法，所以不必再算它的 Sort。Lean 的 `infer_lambda` 同样不会去调 `infer_pi`。

### 2. Lean 的 `infer_only` 会跳过检查

如果一个项早已检查过、kernel 只是想要它的类型，Lean 会传入 `infer_only = true`，此时第 ① 步"A 是类型吗"的检查直接跳过。Rocq 的这个分支没有这种开关。

### 3. 声明里写了 type 时，还要再比较一次

```coq
Definition add2 : nat -> nat := fun n => S (S n).
```

Lambda 分支从函数体算出 `Πn:nat. nat`，而声明里写的是 `nat -> nat`，即 `Π_:nat. nat`。kernel 接着用转换规则比较两者。binder 名字不同（`n` 和 `_`）不要紧，因为 kernel 比较的是 de Bruijn 形式，名字会被忽略。两者一致，声明才能通过。

## 5. 总结

kernel 看到 `Lambda`/`lam` 节点，就套用 λ 引入规则：检查 A 是类型，把 `x:A` 加进上下文，在这个上下文里**递归**算出函数体的类型 B，最后套一层 Π，返回 `Πx:A. B`。

它和 Prod 分支的前两步完全相同，区别在后两步：Prod 检查 B **是不是类型**并算出一个 Sort；Lambda 算出 t **的类型**是什么，并返回一个 Π。依赖的记录方式是：Rocq 靠 de Bruijn 编号自然对上，Lean 靠 `mk_pi` 把 fvar 抽象回 bvar。
