
```coq
Definition length (A : Type@{197}) (l : list A) : nat := …
```
### 起点：Rocq 的全局 Level 是什么
Rocq 的单态声明用的是全局 Level，比如 `length` 用的 197。它是整个环境共享的一个**固定的层**：所有声明里写着 197 的地方都是同一个 Level，它和其他 Level 之间还有全局的大小关系（比如 `Set < 197`）。调用 `length` 时，层永远是 197，更低层的东西靠 Cumulativity 放进来。

Lean 没有全局 Level，可选的翻译只有两种：翻译成一个**具体的值**，或者翻译成一个 **Universe 参数**。两种都不能“直接”用。
### 选项一：直接翻译成具体的值，为什么不行
**第一，我们根本不知道它该是几**。Rocq 只知道 197 比谁大、比谁小，从来没有给它一个具体的数，翻译时没有一个“正确的值”可以填。

**第二，就算随便挑一个，也会把声明锁死在那一层**。比如把 197 翻译成 1：

```lean
def Rocq.length (A : Type 1) (l : Rocq.list A) : Rocq.nat := …
```

Lean 没有 Cumulativity，这个 `length` 就**只能**用在恰好住在 `Type 1` 的类型上，`nat`（在 `Type 0`）就传不进去了。而在 Rocq 中，`length nat l` 是完全合法的。
所以，声明**自己类型里**出现的全局 Level，基本只能翻译成 Universe 参数。
### 选项二：翻译成 Universe 参数，为什么也不能随便
参数解决了“锁死在一层”的问题：

```lean
def Rocq.length.{u_197} (A : Type u_197) (l : Rocq.list.{u_197} A) : Rocq.nat := …
```

每次引用时，`u_197` 都可以选一个合适的层。但 Rocq 全局 Level 的两个性质，参数自己是保不住的：

**第一，共享的关系会丢**。Rocq 中 `length` 和 `count` 用的是**同一个** 197；Lean 中它们各有一个 `u_197`，两个 `u_197` 只是**名字一样**，实际上是两个不同的参数。在 Lean 看来，它们是两个可以各自取任意值的独立参数。这就是“彼此独立”，也就是“共享的关系丢了”。

**第二，大小关系会丢**。Lean 的参数之间写不出任何关系，可以取任何值。Rocq 中 `length` 从来没有在比 197 更高的地方用过，Lean 中却可以把 `u_197` 填得很高。所以每一个选出来的值，都要回头查 Rocq 的关系，确认可以更低、但不能更高；自己的 Level 之间的关系（比如 `Set < 197`）也不能被破坏。

**第三，不是每个全局 Level 都能做成参数。**
- 只在 Body 里出现的 Level，调用者看不到，不需要做成参数；
- 有些 Level 会被 Lean 的类型检查**强制**等于某个值。比如 `natList : Type@{197} := list nat`，值在 `Type 0`，197 就只能是 0，而这又违反了 `Set < 197`，需要换别的翻译方法；
- 有时同一个 Level 在声明里两处的用法，在 Lean 中需要不同的层，一个参数不够，还得拆开。


# 声明自己的类型和 Body 提出的要求（Lean 的类型检查）
翻译完之后，Lean 会把整个声明检查一遍。检查时，有很多地方要拿**两个类型**作比较，要求它们相等。最常见的有三种：
- **调用函数时**：传进去的参数的类型，要等于函数要求的参数类型；
- **把类型交给类型构造器时**：比如 `list A`，`A` 所在的层要等于 `list` 要求的层；
- **整个声明**：值表达式算出来的类型，要等于声明的类型。

如果比较的两个类型里带着 Level，比如一边是 `Type ?m`，另一边是 `Type 0` 或 `Type ?k`，那么“两个类型相等”就会变成一条**关于 Level 的等式**，落到元变量上：
- 一边是空位、另一边是具体值：空位被**定成**这个值（`?k := 0`）；
- 两边都是空位：两个空位被**连在一起**（`?k := ?m`）。

关键在于：Lean 没有 Cumulativity，所以这里要求的是**正好相等**，而不是“不超过”。同样的地方，在 Rocq 里只会产生一个不等式（比如 `197 ≤ id 的层`），记进约束图就行了；到了 Lean，就变成了必须满足的等式。
### 例子
假设 Rocq 中有一个通用的恒等函数 `id`。它是单态的，翻译到 Lean 后带一个参数：

```lean
def Rocq.id.{u} (A : Type u) (a : A) : A := a
```

**例子 1：要求把两个空位连在一起**

```coq
Definition useId (A : Type@{197}) (a : A) : A := id A a.
```

翻译后，197 是 `useId` 自己的 Level，先放空位 `?m`；引用 `id` 时新建一个空位 `?k`：

```text
值表达式：fun A a => Rocq.id.{?k} A a

Lean 检查 Rocq.id.{?k} A a 这次调用：
  id 要求第一个参数的类型是：  Type ?k
  实际传入的 A 的类型是：      Type ?m
  两者必须相等 → ?k := ?m
```

这个要求来自 `useId` 自己的 Body：因为它把自己的 `A` 交给了 `id`，所以 `id` 的层必须和 `useId` 的层**正好一样**。最后 `?m` 没有别的要求，成为参数：

```lean
def Rocq.useId.{u_197} (A : Type u_197) (a : A) : A := Rocq.id.{u_197} A a
```

**例子 2：要求把空位定成具体的值**

```coq
Definition useIdTwice (A : Type@{197}) (a : A) (n : nat) : A * nat :=
  (id A a, id nat n).
```

同一个 `id` 在 Body 里被调用了两次，每次都新建一个空位：

```text
第一次 Rocq.id.{?k1} A a：  传入 A : Type ?m    → ?k1 := ?m
第二次 Rocq.id.{?k2} nat n：传入 nat : Type 0   → ?k2 := 0
```

两次调用各提各的要求：第一次把 `?k1` 连到 `useIdTwice` 自己的层上，第二次把 `?k2` 定成 0。这两个空位互不影响，所以都能满足。

**对比：如果要求落到了声明自己的 Level 上**

```coq
Definition natBox : Type@{197} := list nat.
```

```text
声明的类型：  Type ?m
值的类型：    list nat : Type 0
两者必须相等 → ?m := 0
```

这次要求直接落在 `natBox` **自己的** 197 上，把它定成了 0。而 Rocq 要求 `Set < 197`，两者冲突，Step 7 拒绝。
### 小结
声明的类型和 Body 里的每一次调用，都会对相关的 Level 提出“必须正好相等”的要求，这些要求要等翻译完、让 Lean 检查时才能全部得到。要求落在引用时新建的空位上，一般没问题（例子 1、2）；落在声明**自己的** Level 上、又和 Rocq 的大小关系冲突时，就会失败（`natBox`）。这就是 Level 不能随便选、也不能翻译之前就定下来的原因。

翻译到 Lean 后，声明的类型和 Body 里的每一次调用，都会对 Universe Level 提出新的约束。因为 Lean 没有 Cumulativity，这些约束都是“必须正好相等”，比 Rocq 里对应的“不超过”更严格。所以 Level 要同时满足两边的约束：Lean 类型检查给的等式，以及 Rocq 原有的大小关系。两边冲突时，翻译就会失败。
