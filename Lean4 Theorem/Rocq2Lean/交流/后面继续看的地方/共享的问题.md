你的直觉是对的，而且翻译器已经这样做了。要求"共享就必须正好相等"的只是第一档，也是最严格的一档。后面有一档 **R3↓**（cumulativity tier），做的正是"允许传更低的值"。上一条回复我说这种放宽需要另外搭，这个说法不对，在这里更正。
## sameLength 的例子

```coq
Definition sameLength (A : Type@{197}) (l : list A) (k : list nat) : bool :=
  Nat.eqb (length l) (length k).
```

197 是 `sameLength` 自己的 level，`length` 也用 197。Rocq 里有 `Set < 197`。

在 Rocq 里，两次 `length` 都用在 197 这一层上。`nat : Set` 是靠 cumulativity 被抬进 `Type@{197}` 的。
### 第一档：严格共享，失败
两次调用都必须传 `u_197`：

```lean
Nat.eqb (length.{u_197} A l) (length.{u_197} nat k)
                                         -- ↑ 要求 nat : Type u_197，所以 u_197 := 0
```

Lean 没有 cumulativity，只能把整个声明的 `u_197` 解成 0。这样有两个后果：
- Step 7 的 A1 检查发现 `Set < 197` 被违反，判为 SOLUTION_FACT_VIOLATED。
- 就算不检查，`A` 也只能是 `Type 0` 里的类型，声明变窄了。
### R3↓ 档：每个引用点各用一个新元变量，通过

```lean
def sameLength.{u_197} (A : Type u_197) (l : list.{u_197} A) (k : list.{0} nat) : bool :=
  Nat.eqb (length.{u_197} A l) (length.{0} nat k)
```

- 第一次调用：`A : Type u_197` 迫使它等于 `u_197`。
- 第二次调用：`nat` 迫使它等于 0。
- Step 7 检查 R3，也就是实参不能高于共享 level。Rocq 的 facts 能推出 `0 ≤ 197`，所以这里是往下走，允许。

意思和 Rocq 一样：Rocq 把 `nat` 抬到 197 再数长度，Lean 直接在 0 层数。
## 审计真正守住的是"不能往上"

|实参与共享 level 的关系|Rocq 能不能解释|处理|
|---|---|---|
|相等|能|第一档直接通过|
|更低|能，就是 cumulativity|R3↓ 档允许|
|更高|不能，cumulativity 只能往上抬|REFERENCE_RAISING，拒绝（S25i 里有 28 个）|

所以最终的审计条件是 `≤`，和 Rocq 的 cumulativity 方向一致，并不比 Rocq 严。
## 顺便收回上一条的一个担心
上一条我举了 `AllT` 的例子，担心"往下传会让定理变弱"。实际上 R3↓ 的低值不是随便选的，它只在 Lean 统一被实参迫使时才出现，比如 `sameLength` 里的 `nat`。

像 `P : T -> Prop` 这种参数域上的位置，Lean 本身就要求两边正好相等，降不下去。这和 Rocq 在这里不吃 cumulativity 是同一回事。

没有被任何东西约束的元变量不会被偷偷降低，而是交给 ⑥ 的默认值处理，再验证"填什么都成立"。
