下面是整个流程图。重点是两棵树：**源树 S**（Rocq 一侧）和**目标树 T**（Lean 一侧），以及每一步由谁生成、由谁检查。
## 图 1：从 Rocq 到 Lean 的完整流程

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Rocq 一侧 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Corelib 的 .v 源文件
      │  Rocq 编译
      ▼
  Rocq kernel 里的声明（.vo 中的 Constr.t）          ← Rocq kernel 已检查过
      │
      │  ① MetaRocq quoter                         【可信基：没有独立验证】
      ▼
  MetaRocq Template 项（Coq 里的数据类型）
      │
      │  ② exporter 序列化，不做任何化简
      ▼
  ╔═════════════════════════════════════════╗
  ║  源树 S    文件：source.ndjson            ║  ◄┄ roundtrip：独立解码 → 重新 quote → RtEq 全结构比较
  ║   constant : type / body                 ║  ◄┄ NativeMeta / CheckRelation：元数据和 universe 用原生 Rocq 重算
  ║   inductive: arity / ctors[i].type       ║
  ╚═════════════════════════════════════════╝
      │
      │  ③ IR.lean 严格解析（遇到未知标签就报错）
      ▼
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 翻译 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  翻译器 Rocq2Lean（Lean 代码），按依赖顺序逐条声明处理：
    叶子   rel i → bvar i ｜ const/ind/construct → Rocq.<名>（查注册表）｜ sort → I(sort)
    节点   prod → forall ｜ lam → lam ｜ let → let ｜ app → app
    模板   case/fix → rec ｜ 累积性 → PULift ｜ template sort → Sort u
    universe 元变量由 Lean unifier 解出；构造绑定用 bindFVars，不做 β 化简
      │
      ▼
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Lean 一侧 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ╔═════════════════════════════════════════╗
  ║  目标树 T    Lean 的 Expr（内存中）        ║
  ║   type / value / ctors[i].type           ║
  ╚═════════════════════════════════════════╝
      │
      │  ④ 包装成 Declaration：def / opaque / inductive / 陈述用的 def … : Prop
      │     加上名字和 universe 参数
      │
      │  ⑤ addChecked → addDeclCore (doCheck := true)   【可信基：Lean kernel】
      ▼
  Lean 环境 → .olean          （归纳类型：kernel 在这里自动生成 rec）
      │
      │  ⑥ exprJson：逐个构造子把同一个 Expr 写出来
      ▼
  ╔═════════════════════════════════════════╗
  ║  目标树 T 的 JSON                         ║
  ║   文件：translation_report.json           ║
  ║   target_type / target_value / target_ctors║
  ╚═════════════════════════════════════════╝

━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 独立检查 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  audit    源树 S ──按规则重新计算──► ⟦S⟧  ==?==  report 里的 T     ⇒  T1：同一棵树

  consumer 在新进程里从 .olean 读回声明，和 report 比对                ⇒  环境里的声明就是 report
```

## 图 2：两棵树本身
以 `forall n : nat, n + 0 = n` 为例。左边是 `source.ndjson` 的 `type` 字段，右边是 report 的 `target_type` 字段：

```
源树 S                                         目标树 T
(Rocq / MetaRocq Template)                     (Lean Expr)

prod n                    ── 节点 T02 ──►      forall n
├─ ind nat                ── 叶子 T03 ──►      ├─ const Rocq.…nat
└─ app                    ── 节点 T02 ──►      └─ app
   ├─ ind eq              ── 叶子 T03+U ─►        ├─ const Rocq.…eq.{u}
   ├─ ind nat             ── 叶子 T03 ──►         ├─ const Rocq.…nat
   ├─ app                 ── 节点 T02 ──►         ├─ app
   │  ├─ const Nat.add    ── 叶子 T03 ──►         │  ├─ const Rocq.…Nat.add
   │  ├─ rel 0            ── 叶子 T01 ──►         │  ├─ bvar 0
   │  └─ construct nat 0  ── 叶子 T03 ──►         │  └─ const Rocq.…nat.O
   └─ rel 0               ── 叶子 T01 ──►         └─ bvar 0
```

- **形状相同**：每个节点在同一位置，孩子的个数和顺序都相同。
- **绑定相同**：两个 `rel 0` 和两个 `bvar 0` 都指向最外层的 `n`。
- **叶子对应**：`ind`、`const`、`construct` 都换成注册表里之前翻译好的 `Rocq.<名>`。
- **节点对应**：`prod` 对 `forall`，`app` 对 `app`。
- 为了易读，图里的 `app` 画成了多叉。实际在 Lean 里，`app` 是嵌套的二元应用：`app(app(app(eq, nat), …), …)`。这是规则 T02 的固定写法。
## 三个"等号"连成一条链

```
Rocq 声明  ══①══  源树 S  ──规则 ⟦·⟧──►  目标树 T  ══⑤══  Lean 里被接受的声明
         quoter       │                     │          kernel
       （可信）   roundtrip 检查        audit 检查   replay + consumer 检查
                 序列化和元数据       T = ⟦S⟧       JSON = Expr = 环境里的声明
```

|树|在哪里|谁生成|谁保证它是"对的那棵"|
|---|---|---|---|
|源树 S|`source.ndjson` 的 type / body / ctors|MetaRocq quoter 加 exporter|roundtrip 和原生重算；quoter 本身属于可信基|
|目标树 T|Lean 环境中的 Expr；report 里的 JSON 是它的副本|翻译器按规则生成|kernel 接受它；replay 和 consumer 确认 JSON、环境、report 三者一致|
|S 和 T 的关系|—|规则表 ⟦·⟧|audit 独立重算 ⟦S⟧，逐节点和 T 比较|

整条链上**只有两个可信基**：MetaRocq quoter（Rocq 一侧）和 Lean kernel（Lean 一侧）。中间每一步都有独立的检查。
