机械翻译过程分成三个阶段：
1. General Pipeline：从 Rocq 导出声明和依赖，将源代码表示成 AST，再转换成 Lean Expression。这一部分不区分 Constant 和 Inductive。
2. Declaration Translation：根据声明的种类，分别处理 Constant 和 Inductive Block，尤其是 Universe Levels 的求解和参数化。
3. Kernel Checking：生成正式的 Lean Declaration，注册到 Lean Environment，验证翻译结果。
核心：`trans` 负责把 Rocq Term AST 转换成 Lean Expression；`Emit` 负责利用这些 Expression 构造完整的 Declaration，并确保它们的 Universe、类型与依赖关系正确。
## General Pipeline：所有声明共享的流程
#### Step 1. 从 Rocq Kernel 导出 Declaration 和 Dependency Closure
- 源码：[r2l_export.ml](https://github.com/jackooo-dddd/rocq-core/blob/main/translator/rocq/exporter/src/r2l_export.ml?utm_source=chatgpt.com)。
我们首先需要获得 Rocq 声明的完整信息。
使用 MetaRocq Template Quotation + Rocq Kernel 原生元数据导出，而不是直接解析用户写的 `.v` 文件文本。
原因是 Rocq 的源代码在经过 elaboration 后，很多隐含的信息已经被确定下来，例如隐式参数、实际引用的全局常量、类型、Universe 实例和递归结构。
假设我们有：
```
Definition double (n : nat) : nat :=
  Nat.add n n.
```
- MetaRocq 导出的不只是 `double` 这个 Definition，还要知道它引用了哪些声明，例如 `nat`、`Nat.add`，以及这些声明递归依赖的其他对象。
#### 特别重要：Universe Information
在导出依赖的同时，还必须导出 Universe 信息。它包括以下几种不同层次：

| 信息                    | 内容                                    | 为什么重要                      |
| --------------------- | ------------------------------------- | -------------------------- |
| Universe Levels       | 源声明涉及的层级，如 `u`、`v`                    | 让目标知道需要处理哪些层级              |
| Universe Constraints  | 比如 $u\leq v$                          | 保留 Rocq 对层级之间关系的要求         |
| Universe Instances    | 对某个 polymorphic constant 的具体实例化       | 确定引用某个常量时使用哪个层级            |
| Native Universe Facts | 从 Rocq Universe Graph 得到的关系           | 为后续求解和检查提供依据               |
| Template Metadata     | Template Inductive 的参数与 Universe 绑定关系 | 帮助 Lean 确定 Inductive 的实例层级 |

Universe 关系不能只靠扫描 AST 中出现的 `Type@{u}` 来恢复。
例如，我们可能看到两个 Universe Levels `u` 和 `v`，但单凭 AST 并不能知道 Rocq Kernel 是否已经要求： $u\leq v$ 。 所以当前 Exporter 会另外调用 Rocq 的原生 Universe Graph，获取相关层级间的 `lt` / `le` 关系。
- MetaRocq 提供 AST 和一部分 Universe Context，而原生 Kernel Graph 补充完整的关系事实。翻译器将它们作为后续 Universe 检查的依据。[[Universe Constraints]]
#### Step 2. 对 Declaration 进行分类
![[Pasted image 20261020105043.png]]
 在 Constant 内部，还需要继续分类，例如它是计算定义，还是一个证明。
- 不能仅根据 `Definition` 或 `Theorem` 关键字判断一个 Declaration 是否需要翻译 Proof，关键要看它在 Rocq Kernel 中的 Type 和 Body。例如 `Definition P : Prop := forall n : nat, n = n.` 定义的是一个命题 `P`，它本身是一个返回 Proposition 的 Definition，因此需要保留并翻译其 Body；而 `Theorem p : P.` 定义的是一个类型为 `P` 的 Proof-valued Constant，其 Body 是 `P` 的证明项。
- 对于 `p`，翻译器只翻译其 Theorem Statement `P`，在 Lean 中生成对应的 Proposition Definition，而不翻译原始 Rocq Proof Term。
- Constant 也可能是 opaque data、带有证明依赖的定义，或者 primitive operation。Exporter 会根据 Rocq Kernel 提供的信息判断应该保留哪些内容。
一个容易混淆的概念：`Type` 不是与 Constant、Inductive 并列的第三种顶层 Declaration。一个 Constant 可以定义一个类型，一个 Inductive 本身也会引入一个类型，而 `Type` / `Prop` / `SProp` 是类型系统中的 Sort。
### Step 3. 将 Declaration 表示为 AST
对于普通 Constant，我们通常有 Type AST 和 Body AST；对于 Inductive Block，则会有 arity、parameters、constructors 等多组 AST，而不是简单的两棵树。
以 Constant 为例。
```
Definition double (n : nat) : nat :=
  Nat.add n n.
```
这个声明可以拆成两棵树
![[Pasted image 20261020105849.png]]
- 具体的翻译流程：[[Structural Translation]]
- 这样就可以把一个 Declaration 的类型结构和计算结构转换成可递归处理的树。
- 两棵 AST 不是全部的信息。Declaration 还保留 Universe Context、透明性、relevance、依赖关系等元数据。
- Exporter 最终将这些信息写入 `source.NDJSON 文件`
#### Step 4. 使用 `trans` 将 Rocq AST 转为 Lean Expression
- 源码：[Translate.lean — trans](https://github.com/jackooo-dddd/rocq-core/blob/main/translator/Rocq2Lean/Translate.lean?utm_source=chatgpt.com#L2124)。
现在我们已经获得了类型和正文的 AST。接下来进入 Lean 端的递归翻译：
```
partial def trans (t : IR.Term) : TransM Expr := do
  match t with
  ...
```
这个函数接收一个 `IR.Term`，返回一个 Lean `Expr`。最基础的规则大致如下：

|Rocq AST|Lean Expression|
|---|---|
|`Rel`|对应的局部变量 / `Expr.bvar`|
|`Sort`|`Expr.sort`|
|`Prod`|`Expr.forallE`|
|`Lambda`|`Expr.lam`|
|`LetIn`|`Expr.letE`|
|`App`|`Expr.app`|
|`Const`|`Expr.const`|
|`Inductive reference`|已注册的 Inductive 引用|
|`Constructor reference`|已注册的 Constructor 引用|

例如：
```
Rocq:
  Lambda(n, nat,
    App(Const(Nat.add), [Rel(0), Rel(0)]))

              ↓ trans

Lean:
  Expr.lam(n, ...)
    Expr.app(...)
```

对普通 Lambda、应用和绑定变量，这个过程主要是结构上的映射。
不过，`trans` 还必须能够处理不能简单一一对应的节点。例如：
- `Case` / `Match`：需要构造 Lean 的 Recursor application。
- `Fixpoint`：可能需要结构递归或其他受检查的 lowering（M 类机制）。
- `Cast`：可能需要检查 definitional equality，或者引入显式表示转换。
- `Sort` 和 Constant reference：须根据当前 Universe Context 生成 level 实例（R 类机制）。
暂时不展开这些额外规则，只要知道：`trans` 是一个以递归 AST 翻译为主体、在必要节点调用专门转换逻辑的统一入口。
还有一个关键点：`trans` 是要记录上下文的。
- 翻译一个 `Const` 时，它必须知道这个常量是否已经在 Lean Environment 中注册，以及它的 Universe Parameters。
- 翻译一个 `Rel` 时，它必须知道当前作用域内有哪些局部变量。
- 翻译 `Sort` 时，也必须知道源 Universe Level 当前对应哪个 Lean Level。
这些信息由翻译上下文 `TCtx` 和全局环境记录 `GEnv` 提供。
### Step 5. 从 Expression 进入 Declaration Translation
[[Expression VS Declartion]]
到这里，翻译器已经具备将 Rocq Term 转换成 Lean Expression 的通用能力，但这并不意味着翻译已经完成。
因为 **Lean Expression 只是一个表达式，要将它正式加入 Lean Environment，还需要生成完整的 Lean Declaration**，包括处理 Declaration Name、Type、Body、Universe Parameters 和 Dependencies 等。这一步主要由 `Emit.lean` 负责调度。
