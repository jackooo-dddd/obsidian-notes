In most declarations no cumulativity is involved at all: each Rocq universe level becomes its own Lean universe parameter, and nothing has to be merged or lifted. These are counts over the 2,180 Corelib roots in the current (patched) translation:

| How the universes came out                                                | Roots |
| ------------------------------------------------------------------------- | ----- |
| No universe parameters at all                                             | 949   |
| Has universe parameters                                                   | 1,231 |
| Some level solved by unification (fixed to an expression of other levels) | 128   |
| `max` in the Lean type                                                    | 105   |
| Type-to-Type lift used                                                    | 47    |
| `PULift` anywhere in type or value                                        | 50    |
| `PULift` in the statement itself                                          | 18    |
| Result type lowered to the value’s level                                  | 23    |
| Prop-to-Type lift (rule P)                                                | 3     |
| Levels read as `max …` before elaboration                                 | 2     |

The rows overlap; one root can appear in several.

**In short:**

1. **The normal case (about 90%):** plain parameters, where Rocq’s levels map one-to-one to Lean’s. Lean’s unifier still runs on every declaration, but here it only confirms what Rocq already says.
2. **The next most common (128):** unification solves a level as an expression of others. For example, the level of `A → B` becomes `max u v`, or a level that typing forces equal to another is merged. This is accepted only when Rocq’s constraints allow it. For input universes of theorems and protected declarations, the merge must be implied by Rocq’s constraints; the new check enforces that.
3. **The rare fallback (about 50):** `Type (max u v)` plus `PULift`, needed only where Rocq relies on cumulativity that Lean can’t express any other way. Two examples are `ssr_congr_arrow` and the Type-valued relations in `Morphisms`/`RelationClasses`. The translator tries these lift attempts after the ordinary ones fail, so a lift appears only when it is needed.
