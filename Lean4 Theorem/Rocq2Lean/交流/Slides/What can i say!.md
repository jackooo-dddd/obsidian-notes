## 0. 我们的翻译能保证什么
### 0.1 什么叫「翻译正确」
同时满足下面五条：

1. 按规则翻译：使用我们定义的规则，按节点进行翻译。
2. 目标端直接合法：翻译过去的东西，不需要任何额外转化，在 Lean 里就是合法的。
3. 计算保持：Rocq 里成立的计算，翻译后在 Lean 里也成立。
4. 可证性保持：Rocq 能证明 T，Lean 就能证明 ⟦T⟧。
5. 依赖已就绪：对每个翻译的声明，它引用的声明、依赖的常量的类型，都已经翻译好了。
### 0.2 用了翻译器，能保证什么
只要你接受规则表（叶子、Sort 映射、组合方式）中的每一条，你在 Lean 中拿到的每个陈述，就是原 Rocq 陈述的忠实重写：

- 没有增加、没有遗漏、没有错位、没有猜测；
- 同一种结构，处处用同一种翻译。

> [!summary] Rocq AST 和 Lean `Expr` 是同一棵树
> 接受规则表之后，经过机械的翻译：
> - 形状相同：每个位置一一对应；
> - 绑定结构相同：变量指向对应的绑定；
> - 叶子换成它的对应物：在字典（或 Sort 映射）中查到的对应物，也就是翻译当前声明时，之前已经翻译好的声明的 Rocq → Lean 映射；
> - 组合节点换成它的对应节点，或者对应的固定模板。
>
> 除了规则表里明文列出的几处例外，没有任何增加、删除或调换。
### 0.3 为什么按规则翻译就正确：结构归纳
规则分两类：叶子和组合方式。

**叶子：项里不能再拆的部分**

| 规则 | Rocq → Lean | 说明 |
|---|---|---|
| T01 变量 | `Rel i` → `bvar i` | 编号 i 不变，因为外层的绑定结构（Π / λ / let）被原样保留了 |
| T03 常量引用 | `nat`、`add`、`eq`、`O` → `Rocq.nat`、`Rocq.add` 等 | 对已有声明的引用，附上对应的 Universe 实例 |
| U02 Sort | `Prop` → `Sort 0`；`Type(l+n)` → `Sort(I(l)+n+1)` | |

**组合方式：把较小的项拼成更大的项**

- T02：Π（`Prod` → `forallE`）、λ（`Lambda` → `lam`）、let（`LetIn` → `letE`）、应用（`App` → `app`）。这四种两边一一对应，逐字段翻译，子项递归翻译。
- M、L：`case`、`fix`、累积性等，对应 Lean 里的固定模板。

T02 的关键性质：两边类型规则相同，并且与替换交换，即 ⟦t[u/x]⟧ = ⟦t⟧[⟦u⟧/x]。所以每条规则只需论证一次，之后可以任意嵌套使用。

**论证分四步**

1. 叶子对应：变量按上下文对应；常量指向之前已经确认的声明。常量之所以正确，是因为它引用的声明本身就是用同样的方法翻译、并且已经验证过的。
2. 组合节点对应：每个 Rocq 组合节点，对应 Lean 里一个节点或一个固定模板，两者的类型规则和意思相同，孩子放在对应位置。
   - 对 Π、λ、let、应用（T02）：是同一种节点；
   - 对 `case`、`fix`、累积性（M、L）：每一族需要单独证明一次。
3. 组合引理：如果一个组合节点的每个孩子，在对应的上下文里都和它的翻译对应，那么整个节点也和它的翻译对应。
4. 结论：从叶子开始，反复使用 3，一直到树根，整棵 AST 和翻译出来的 Lean `Expr` 对应。这就是对单个声明内部的项结构做归纳。

> [!note] 对两棵 AST 各做一次
> 一个声明有 Type AST 和 Body AST 两棵树（见 [[Structural Translation]]）。上面的归纳对两棵树各做一次：Type AST 得到 Lean 类型表达式，Body AST 得到 Lean 值表达式，两者合起来生成 Lean declaration。

## 1. 证明助手之间翻译的正确性
可以从三个层次来说：

1. 目标端合法：翻译得到的类型、定义和命题，符合目标语言的规则；如果还生成了证明，这个证明必须确实证明了目标命题，并通过目标 Kernel 的检查。
2. 逐规则保持对应：**先证明小的部分翻译正确，再一步步证明由这些小部分组成的复杂表达式也翻译正确**。首先定义两个语言中最基本的东西是怎么对应的，比如 Rocq 的自然数和 Lean 的自然数怎么对应、两边的值和命题怎么对应。然后，分别检查每一种语法规则，比如变量、函数定义、函数调用等，证明只要组成它的几个小部分在翻译前后保持对应，那么用这条规则组合出来的新表达式也一定保持对应。最后，因为任何复杂的表达式都是通过这些基本规则一层一层构建出来的，所以我们可以使用数学归纳法，把前面证明过的规则不断应用到更大的表达式上，最终证明整个表达式的翻译都是正确的。简单来说，先确定最基本的东西表达相同的意思，再证明每一种组合方式不会改变原来的意思，最后就能保证由这些规则构成的整个表达式在翻译后仍然保持原来的含义。
3. 放进同一个逻辑框架比较：把两边放进同一个逻辑框架，在框架里比较。把 HOL、Coq、Lean 中的类型、命题、证明等翻译到 Dedukti，使它们可以在同一个逻辑框架中表示。说明两边翻译后的对象怎样对应。例如，HOL 中的自然数和 Coq 中的自然数是否表示同样的数学对象。在建立对应关系的基础上，证明两个命题等价。

> [!note] 对比：同一个系统内的 proof transfer
> 同一个系统内，不同表示之间的命题等价：给定一系列等价关系，把一个命题自动变换成另一种表示下的命题，并生成两者之间的转换证明。这和跨系统翻译不是一回事。
## 2. 逐规则 + 归纳：编译正确性的标准思路
每一种 AST 构造的翻译规则，都要能把已经对应的子表达式，组合成仍然对应的父表达式。

CompCert 官方手册就用 `a + b` 举例：先通过归纳假设得到 `a`、`b` 的翻译正确性，再结合 `+` 自己的正确性论证，推出整个表达式的正确性。

| AST 构造或翻译操作              | 对应规则必须保证什么                                |
| ------------------------ | ----------------------------------------- |
| 变量                       | 引用的是对应的绑定位置，没有拿错变量或产生变量捕获                 |
| 常量引用                     | 引用的是已经对应的声明，类型参数与 Universe Instance 按规定对应 |
| 函数应用                     | 对应函数应用于对应参数，得到对应结果                        |
| Lambda / Π 类型            | 扩展后的变量环境、参数类型和 Body / 结果类型保持对应            |
| Let / 替换                 | 把值代入表达式，与翻译操作相容                           |
| 构造子 / `match` / recursor | 构造子、分支参数、依赖返回类型和计算规则对应                    |
| 递归定义                     | 递归调用和所使用的归纳、终止依据足以建立结果对应                  |
| Sort / lift / transport  | 层级调整、包装和类型转换保持规定的类型与值关系                   |
## 3. 前提：先形式化两边的语言
证明两个语言一致，首先要形式化这两个语言：两侧的核心语法、类型规则和必要的求值行为。

Lean 和 Rocq 的语义都由一个小内核加一套类型论决定。

**什么是内核，为什么小**

- 语法只有十来种构造：sort、Π、λ、应用、let、常量、归纳类型、消去。
- 类型规则十几条，外加一个由 β / δ / ι / ζ / η 生成的定义相等。
- 没有未定义行为：每个良类型的项都有确定的意思，不良类型的项直接被拒绝。

**谁规定意思**

内核类型检查器，加上它所实现的类型论。项目里用到的就是 PCUIC 和 Lean 的类型论。
## 4. 总共有哪些环节要考虑

| 实际环节 | 需要建立的连接 |
|---|---|
| Rocq declaration → 导出的 AST / IR | 导出的类型、Body、绑定、常量引用、Universe 信息确实对应原声明 |
| IR → Lean `Expr` | 实际采用的翻译和适配步骤，符合已证明正确的规则 |
| 生成的 `Expr` → 最终 Lean declaration | 实际进入环境、保存到产物中的 type、Body 和参数，就是接受检查的对象 |
| 最终声明及依赖 | 目标通过 Kernel 检查，所依赖的假设或未完成义务被准确计入结论 |
