## 额外的规则（转接头）
**为什么需要：** Rocq 有两样 Lean 没有的东西：

- Cumulativity：低层 Universe 的东西可以直接当高层用；Lean 要求层正好相等。
- Universe 约束：Rocq 的 Level 之间可以写 `v < u` 这样的约束；Lean 的参数之间写不出约束，每个参数都能取任何值。

基本的 Level 求解（统一）处理不了的地方，就要靠下面这些「转接头」顶替 Rocq 的那一步。每个转接头都有代价，所以翻译后还要做 Generality Loss 检查，确认没有把声明变窄。
### 总览

| 转接头 | 顶替 Rocq 的哪一步 | 代价 |
|---|---|---|
| R3↓ | Cumulativity（低层当高层用），在引用处 | 引用处不再严格共享，需要层无关性的论证 |
| 约束编码（`max`） | 全局 / 局部约束（`v < u`） | 参数形状改变，要说明合法取值一一对应 |
| ULift / PULift | Cumulativity，在选不了层的地方 | 只到同构，项的形状改变 |
| 良基递归 | 非结构递归的 `fix` | 依赖终止性 Obligation，计算变弱 |

> [!note] A 类和 B 类声明
> A 类声明一个转接头都不用，所以能用现成理论一次论证完。只要用到其中任何一个，就归到 B 类，交给逐个证书去检查。
### 0. 基础机制（不算转接头）
这两种是翻译的常规做法，不改变项的形状，列在这里方便对照。

**Unification（Universe Level 求解）**

- 解决什么：Lean 类型检查中两个 Level 需要匹配；Monomorphic 声明自己的全局 Level 需要求解；同一个源 Level 在多处引用中要保持一致（Coherence）。
- 怎么做：创建 Universe 元变量，通过类型检查和 `solveLevels` 求解。解可以是另一个 Level（`?u := ?v`）、Level 表达式（`max(u, v)`、`u+1`），也可以是常量 `0`。未被求解的公开 Level 可以 Generalize 为 Lean 参数。
- Generality 检查：
  1. 解必须满足 Rocq 原有的 Universe 约束；
  2. 不能合并两个原本独立的公开输入 Level，除非 Rocq 已强制它们相等；
  3. 不能把 Rocq 中仍自由的 Level 固定为常量。例如只有在源约束强制它不高于 `Set` 时，才能固定为 `0`。

**`max`：计算结果 Universe**

- 解决什么：结果类型由多个类型组成时（Pair、Sum、Record），它的 Universe 必须足够高，可能由多个输入 Level 决定。
- 怎么做：用 `max` 计算，例如 `Type (max u v)`，不需要统一 `u`、`v`。
- Generality 检查：不需要额外的防合并检查，因为 `u`、`v` 保持独立。
### 1. R3↓：引用时往低层取
**为什么需要**

Rocq 中某个常量引用在较高的 Universe 上使用，靠 Cumulativity 接受了较低 Universe 的输入。Lean 要求层正好相等，于是对不上。这种情况可能出现在声明类型、Body，或前提假设的实例化中。

**怎么做**

降低被引用常量的 Universe Instance，而不是改变输入类型。例如 `T : Type u`，原来用的是 `pred.{v} T` 且 `u ≤ v`，翻译后改成 `pred.{u} T`，直接匹配 `T` 的 Level。

**例子**
```coq
Definition sameLength (A : Type@{197}) (l : list A) (k : list nat) : bool :=
  Nat.eqb (length l) (length k).
```
- Rocq：两次 `length` 都在第 197 层用，`nat`（在 `Set` 层）被 Cumulativity 抬了上去。
- Lean：如果严格共享，两次都只能传 `u`，而 `nat` 在第 0 层，于是对不上。
- 转接头：第二次调用改成在第 0 层用：
```lean4
Rocq.Nat.eqb (Rocq.length.{u} A l) (Rocq.length.{0} Rocq.nat k)
```
**Generality 检查**

- Never Raise：调整后的 Level 必须 `≤` Rocq 原来的 Level；
- 只能降低类型检查能确定的引用 Level，不能把自由的引用 Level 随意固定为 `0`。

**代价：** 引用处传的不再是「同一个 Level」。要说明意思不变，需要「只换了装它的层、集合没变」那条层无关性的论证。
### 2. 约束编码：把 Rocq 的约束写进 Level 本身
**为什么需要**

有些 Rocq 声明之所以合法，靠的是 Universe 约束（比如 `v < u`）。Lean 的参数之间写不出约束：如果直接翻译成两个独立参数，Lean 不知道它们之间的大小关系。Monomorphic 的全局约束、Polymorphic 声明自己的约束（如 `u + k ≤ v`）都会遇到这个问题。

**怎么做**

建立 Universe Interpretation，把约束放进 Lean 的 Level 表达式里。例如 `I(v) = max(v, u+k)`，这样不管参数取什么值，`u+k ≤ I(v)` 都成立。

**例子**
```coq
Inductive box : Type@{u} := mk : Type@{v} -> box.   (* 约束：v < u *)
```
- Rocq：字段在第 `v` 层，自己在第 `u` 层，因为 `v < u`，所以合法。
- Lean：`u`、`v` 是独立参数。取 `u = 0`、`v = 5` 时，「字段的层不超过自己的层」就不成立，Lean 拒绝。
- 转接头：把 `u` 写成 `max (v+1) w`：
```lean4
inductive box.{v, w} : Type (max (v+1) w) where
  | mk : Type v → box
```
不管 `v`、`w` 取什么，`max (v+1) w` 总比 `v` 大，约束自动成立。

**Generality 检查**

- Interpretation 必须满足所有 Rocq 原有的约束；
- 原本合法的 Universe 取值必须仍然可以表示，不能因为编码而缩小 Generality。

**代价：** 声明的参数变了，从 `u, v` 变成了 `v, w`。要说明对每个满足 `v < u` 的取值，都能取 `w := u` 还原回来。
### 3. ULift / PULift：显式往上包一层
**为什么需要**

有时没法「选一个正好的层」：比如那个层已经被别的地方定住了，只能把东西包装一下，抬上去。常见的情况：

- Type → Type：较低 Universe 的类型被用在较高 Universe 的位置；
- Prop → Type：命题被用在要求 Type 的位置；
- 在参数、`let` 值、函数头等内部表达式中需要处理 Cumulativity；
- Proof 模式中的 cast、`match` 返回类型等，也需要显式转换。

**怎么做**

构造 `PULift` 包装类型，必要时在项中插入 `PULift.up` / `.down`。例如 `P : Prop` 转换为 `PULift.{1,0} P : Type 0`。对 Type → Type 的提升，保留较高 Universe 的独立参数，而不是强制它等于较低的 Level。通常在普通翻译尝试失败后才启用。

**例子一（ULift）：** 一个单态的结构，层由共享固定在 `u`，要放一个第 0 层的类型进去：
```coq
Record Pack := { carrier : Type@{l} }.               (* l 与别处共享，不能随便降 *)
Definition natPack : Pack := {| carrier := nat |}.   (* Rocq：nat 被 Cumulativity 抬上去 *)
```
```lean4
def natPack : Pack.{u} := ⟨ULift.{u} Rocq.nat⟩    -- 包一层，抬到第 u 层
```
**例子二（PULift）：** Rocq 里命题可以当类型用（`Prop ≤ Type`）：
```coq
Definition proofs (P : Prop) := list P.     (* Rocq 允许：Prop 被抬成 Type *)
```
```lean4
def proofs (P : Prop) := Rocq.list (PLift P)   -- Lean 里 Prop 不能直接当 Type 用，要包一层
```
我们的 `PULift` 把这两种情况合在一起：把命题或低层的类型，包装后抬到需要的层。

**Generality 检查**

- 满足 Rocq 原有的 Universe 约束，同时保留原本合法的取值。例如源中是 `u < v`，就不能通过强制 `u = v` 来缩小 Generality；
- 包装后的类型表达式和值表达式必须通过 Lean Kernel 和相应的翻译检查。

**代价：** `ULift A` 和 `A` 只是同构，不是同一个类型。项的形状变了，用到的地方要配 `.up` / `.down`，意思也只能保留到「同构」。

> [!tip] `max` 和 `PULift` 解决的是两个不同的问题
> - `max`（约束编码）：保证 Level 之间的约束关系成立，比如 `v₀ ≤ I(v₅)`；
> - `PULift`：显式处理依赖 Cumulativity 的类型提升。
>
> 即使用 `max` 保证了 `v₀ ≤ v₅`，Lean 仍然不会自动把 `Type v₀` 中的类型当作 `Type v₅` 中的类型用。所以 `max` 本身不能消除 Lean 的类型不匹配，还需要 `PULift`。如果这些方法都无法产生安全的翻译，就拒绝这个翻译候选。
### 4. 良基递归：不是结构递归的函数
**为什么需要**

结构递归（每次在更小的子项上递归）可以直接改写成 recursor。但有些递归函数不是在子项上递归，比如 `gcd`：它的参数变小了，却不是原来参数的子项。这种只能用良基递归来表达。

**例子**
```coq
(* Rocq：用 measure / Fix + well_founded 定义 *)
gcd a b := if b = 0 then a else gcd b (a mod b)
```
```text
翻译后：用 Acc.rec，并附一个终止性 Obligation：
  "a mod b < b"（每次递归，量确实在变小）
```
**代价**

- 函数的意思不变（递归定理：满足同一组方程的函数唯一），但依赖那个终止性 Obligation。Obligation 没证完之前，定义是有条件的。
- 计算会变弱：`Acc.rec` 要等终止性的证明化简成 `Acc.intro` 才能往下算，而证明一般是不透明的，所以 `rfl`、`decide` 常常算不动。

## Monomorphic 和 Polymorphic 用到的转接头不同

| | Monomorphic | Polymorphic |
|---|---|---|
| Rocq Universe | 全局 Universe Level | 声明自己的 Universe 变量 |
| Lean 参数如何产生 | 创建元变量，求解后 Generalize | 通过 R6 直接映射到 Lean 参数 |
| Unification 求解的 Level | 125 个 | 0 个 |
| R3↓ | 23 个 | 0 个 |
| `max` | 49 个 | 41 个 |
| `PULift` | 24 个 | 26 个 |

- Monomorphic：简单的直接映射；复杂的，把全局 Level 转成 Lean 的 Universe 参数，需要求解。
- Polymorphic：Universe 变量直接对应 Lean 参数，不需要对自己的参数做元变量求解，但仍然大量用到 `max` 和 `PULift`。

**为什么 Polymorphic 仍需要 `max` 和 `PULift`**

即使 Polymorphic 声明已经有了 Universe 参数，参数之间的约束（例如 `v₀ ≤ v₅`）也不会自动被 Lean 保留，所以要用 `max` 编码，例如 `I(v₅) = max(v₀, v₅)`。而 Lean 没有 Cumulativity，较低层的类型要用在较高层，还得靠 `PULift`（见第 3 节末尾的提示）。

**为什么 Polymorphic 不需要 R3↓**

引用一个 Polymorphic 常量时，源 AST 已经写明了 Universe Instance，例如 `respectful@{v₀ v₁ v₂ v₃ v₄ v₅}`。翻译器通过 R6 把这些 Level 逐一映射到 Lean：

- `Set` → `0`；
- Universe 变量 → 对应的 Lean 参数；
- 全局 Level → 当前声明中对应的 Level Interpretation。

这些 Instance 是 Rocq 指定的，翻译器不能像 R3↓ 处理 Monomorphic 引用那样，为了匹配输入而随意选更低的 Level，否则可能改变原始引用的 Universe 语义。

> [!example] Polymorphic 怎么处理 Cumulativity
> 假设 `A : Type@{v₀}`，某个引用 `foo@{v₁}` 要求输入在 `Type@{v₁}` 中，且有约束 `v₀ ≤ v₁`。Rocq 靠 Cumulativity 接受，但 Lean 中 `foo.{v₁} A` 可能过不了类型检查。由于不能把 `foo` 的 Instance 从 `v₁` 降成 `v₀`，翻译器改用：
> - `max` Interpretation（例如 `I(v₁) = max(v₀, v₁)`）编码源约束；
> - `PULift` 显式把 `A` 从低层抬到高层。
