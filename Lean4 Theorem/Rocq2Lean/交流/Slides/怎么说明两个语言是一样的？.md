**要证明两种语言之间的翻译一致，难点在别处：**
1. **语言本身的语义有争议或者是由实现决定的。**
    - C 标准有大量未定义行为，内存模型至今仍有争论。
    - Python 实际上以 CPython 的行为为准，还有 `eval`、运行时可以改类这类动态特性。
2. **标准库和运行时才是大头。** 真实程序会调用 libc、Python 标准库、操作系统，这些几乎都没有形式化。前面看的 TransCoder 和 AlphaTrans，主要难点也在"标准库怎么对应"。
3. **两边都得形式化，还要在同一个证明系统里。** 比如 C→Rust，Rust 一侧目前只有部分形式化，如 RustBelt/λRust、MiniRust、Aeneas，覆盖都不完整。
4. **"一致"本身就要先定义。** 源程序有未定义行为时，"意思相同"无从谈起。所以 CompCert 用的是"源程序不出错时，两边行为一致"，这是 refinement 的形式，不是完全等价。
5. **工作量**：CompCert 一个编译器就投入了多人年。

**实际可行的路线，都是缩小范围：**
- **限定子集，证明翻译器正确**：CompCert 只处理它形式化了的那个 C 子集。Scylla 把"在源语言层面证明语义等价"列为未来工作。
- **逐次验证，不证明翻译器**：只要有两边的语义模型，就能对每一次翻译单独检查，像 Alive2 用 SMT 那样。这比证明整个翻译器容易得多，但通常有界，而且语义模型本身也在可信基里。
- **退一步，证明更弱的性质**：比如类型保持（TAL）、内存安全，而不是完整的语义等价。

**和证明助手的对比：** 证明助手的"语言"就是一个小内核加一套类型论，规模比 C 或 Python 小得多，而且已经有现成的形式化，比如 MetaRocq 的 PCUIC、Lean4Lean。所以在 Rocq→Lean 这种场景下，一般性定理在原理上比 C→Python 可行得多。不过 Holide、Cousineau–Dowek 这类工作也只是对核心演算证明的，不是对整个真实系统。

### Lean/Rocq：语义由一个小内核加一套类型论决定
**谁规定意思**：内核类型检查器，加上它所实现的类型论。项目里用到的就是 PCUIC 和 Lean 的类型论。

**为什么小**：
- 语法只有十来种构造：sort、Π、λ、应用、let、常量、归纳类型、消去。
- 类型规则十几条，外加一个由 β/δ/ι/ζ/η 生成的定义相等。
- **没有未定义行为**：每个良类型的项都有确定的意思，不良类型的项直接被拒绝。
- **没有副作用、没有内存模型、没有 I/O**：项是纯数学对象。
- **没有"标准库属于语言"的问题**：库只是用内核语言写的定义，内核不需要知道它们。
- **表层语言不在可信基里**：tactic、elaborator、记号都可以很复杂，但最后都要被内核检查（de Bruijn 准则）。
