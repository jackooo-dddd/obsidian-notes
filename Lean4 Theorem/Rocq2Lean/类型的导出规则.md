在 Rocq2Lean 中，我们可以把需要翻译的东西分成几个大类，例如 Type、Definition、Operation、Theorem、Proof 等。但首先要区分：这些是方便理解的语义分类，并不全都是 Rocq 内核中的 declaration 类型。

实际上，你现在的 [Rocq2Lean](https://github.com/jackooo-dddd/Rocq2Lean) 导出器在顶层只区分两种：

1. `Inductive`：归纳类型及其 constructors。
    
2. `Constant`：普通定义、函数、运算、定理、证明和公理等。
    

其他区别主要体现在这些 declaration 的类型、内容以及是否有 proof body。

## 1. 先列出所有主要类别

|类别|Rocq 例子|作用|
|---|---|---|
|Sort / Universe|`Prop`, `Set`, `Type`, `SProp`|表示类型所在的层级|
|Inductive / Datatype|`nat`, `list`, `eq`, `bool`|定义新的类型及其构造规则|
|Constructor|`O`, `S`, `nil`, `cons`, `eq_refl`|构造归纳类型的元素或证明|
|Record / Structure|`Record JobInfo := ...`|定义带有字段的结构|
|Type Alias|`Definition instant := nat`|给已有类型或类型表达式定义一个名称|
|Definition / Value|`Definition zero := 0`|定义一个普通值|
|Function / Operation|`add`, `min`, `completed_by`|接受输入并返回结果|
|Recursive Function|`Fixpoint add ...`|定义递归函数|
|Theorem / Lemma|`Theorem ...`, `Lemma ...`|声明需要证明的命题|
|Proof Term|`eq_refl`, `fun ... => ...`|给出命题的具体证明|
|Axiom / Parameter|`Axiom P : Prop`|声明没有提供证明体的假设|
|Class / Instance|`Class JobArrival ...`|定义类型类及其实例|
|Notation / Hint / Tactic|`Notation`, `Hint`, `Ltac`|辅助写代码或构造证明，不一定成为独立的内核声明|

有两个重要区别：

- `Type` 本身通常是一个 sort，不是一种和 `Theorem` 平行的 declaration 类别。`nat : Set` 表示 `nat` 是一个类型，而 `Inductive nat` 才是在定义这个类型。
    
- `Operation` 也不是独立的 declaration 类别。例如 `Nat.add` 是函数，底层仍然属于 constant；一个 `+` 符号也可能只是 notation。
    

## 2. 这些类别在 Rocq2Lean 中分别怎么导出？

根据仓库的 [IR_SPEC.md](https://github.com/jackooo-dddd/Rocq2Lean/blob/main/docs/IR_SPEC.md) 和 [Emit.lean](https://github.com/jackooo-dddd/Rocq2Lean/blob/main/Rocq2Lean/Emit.lean)，可以整理成下面这张表：

|Rocq 源代码|导出到 Source IR|翻译到 Lean|
|---|---|---|
|`Inductive nat ...`|`inductive`|Bootstrap → `Nat`|
|`Inductive list ...`|`inductive`|生成新的 Lean inductive|
|`Record ...`|`inductive`|支持的 Record 生成 Lean 归纳结构|
|`Definition instant := nat`|`constant`（transparent）|Lean `def`|
|`Definition f ... := ...`|`constant`（transparent）|Lean `def`|
|`Fixpoint f ...`|`constant`，body 中包含 `fix`|使用递归 lowering，最终生成 Lean `def`|
|`Theorem ... Qed.`|`constant`（opaque_present）|Lean `theorem`，如果目标类型是 `Prop`|
|`Lemma ... Qed.`|`constant`（opaque_present）|同上|
|`Axiom ...` / `Parameter ...`|`constant`（assumption）|当前项目拒绝，不添加新公理|
|`CoFixpoint ...`|`constant`，body 中包含 `cofix`|当前不支持|

这里还有一个细节：如果证明用 `Defined.` 结束，proof body 是 transparent 的，当前翻译器通常把它生成为 Lean `def`，而不是根据 Rocq 中写的是 `Lemma` 还是 `Theorem` 决定。也就是说，翻译规则主要看内核声明的类型、body 和透明性，不看最初使用的语法关键词。

## 3. 一个 declaration 内部还有哪些需要翻译的东西？

例如：

```
Definition double (n : nat) : nat :=
  Nat.add n n.
```

整体属于一个 `constant`，但里面还包含很多更小的表达式，翻译器需要分别处理：

|内部表达式类别|例子|翻译方式|
|---|---|---|
|Sort|`Prop`, `Set`, `Type`|转成 Lean `Sort` 层级|
|Function Type|`nat -> nat`|Lean 函数类型|
|Lambda|`fun n => ...`|Lean `Expr.lam`|
|Application|`f n`|Lean `Expr.app`|
|Local Let|`let x := ... in ...`|Lean `Expr.letE`|
|Global Reference|`Nat.add`|查找已翻译的对应声明|
|Constructor Reference|`S n`|查找对应 constructor|
|Pattern Matching|`match ... with`|降到 Lean recursor|
|Recursion|`fix`|通过受支持的 recursion lowering 转换|
|Projection|`record.field`|翻译字段访问|
|Cast|类型转换标注|检查类型后处理|
|Proof Term|`eq_refl`、证明中的 `match`|按表达式规则翻译并由 Lean kernel 检查|

还有一类东西，比如 `Notation`、`Section`、`Variable`、`Hint` 和 `Ltac`，通常不作为独立的数学 declaration 导出。它们在 Rocq elaboration 阶段发挥作用，其影响可能已经体现在最后的类型、参数、proof term 或环境声明中。例如，`Section` 里的变量在 Section 结束后，可能成为实际使用它们的 definition 或 theorem 的参数。

所以接下来讨论不同类型的翻译规则，最合理的顺序是：先看 `Inductive / Datatype`，再看 `Definition / Operation`，最后看 `Theorem / Proof Term`。 其中前两者主要解决类型和计算结果怎么对应，最后一类则涉及证明项如何翻译、如何通过 Lean kernel 验证。
