**第一类是“把各个部件换成 Lean 的对应部件，整体结构基本不变”；第二类是“原来的结构不能直接搬过去，需要换一种组织方式”。**
## 1）直接对应：部件逐项翻译，组合方式基本不变
主要包括下面这些：

|类别|例子|翻译时做什么|
|---|---|---|
|基础类型、构造器的对应|`nat → Nat`，`S → Nat.succ`，`eq → Eq`|使用事先确定好的对应对象|
|基本表达式的对应|函数应用、`fun`、`∀`、`let`|分别翻译里面的各个部分，再按相同的结构组合起来|
|已翻译声明的引用|`f → fL`|查映射表，找到 `f` 已经生成的 Lean 声明，直接引用它|

其中，函数应用、函数抽象、全称量化和局部绑定，都是 Lean 底层表达式能够表示的基本结构。[arXiv](https://arxiv.org/html/2403.14064v2?utm_source=chatgpt.com)
例如，按照前面约定的自然数映射：
```
Rocq：fun (n : nat) => S n
Lean：fun (n : Nat) => Nat.succ n
```
这里没有重新设计函数：参数类型从 `nat` 换成 `Nat`，构造器从 `S` 换成 `Nat.succ`，**“输入一个数，再返回它的后继”这个结构保持不变。**
注意，`f x → fL xL` 不需要为每个函数写一条新规则。只需要一条通用规则：**先翻译函数 `f`，再翻译参数 `x`，最后把它们组合成函数应用。**

## 2）结构转换：换一种组织方式，实现原来的意思

比较典型的是下面三种：

|类别|简单理解|
|---|---|
|`match`，也就是分类讨论|把“判断哪个构造器、每个分支返回什么”等信息，重新组织成 Lean 底层的分情况处理机制|
|`fix`，也就是递归定义|分析“在哪个参数上递归、每一步怎样调用自己”，再用 Lean 支持的递归机制构造出来|
|Universe，也就是类型层级|两边对类型层级的规定不同，需要分析各个类型之间的关系，确定 Lean 中应该使用哪些层级和参数，而不是仅把 `Type` 换成 `Type`|

**这里不是说 Lean 没有 `match` 或递归函数。** Lean 表面上也能这样写，但底层会把它们转成归纳类型提供的 _recursor_，可以理解为“分情况处理和递归计算的基本工具”。我们的底层翻译需要完成这种结构上的组织，而不只是替换关键词。[Lean Language](https://lean-lang.org/doc/reference/latest/The-Type-System/Inductive-Types/?utm_source=chatgpt.com)

Universe 也是类似的情况：Rocq 和 Lean 的类型层级规则确实不同，因此不能认为同样写着 `Type`，就一定能原样对应。[Lean Language](https://lean-lang.org/faq/?utm_source=chatgpt.com) **转换必须保留原来的含义；没有合适转换方法时，应当报告不支持，而不是随便修改约束让它通过。**

所以，你原来的那段话可以简化成：

> 翻译器里主要有两类规则。一类比较直接，比如把 `nat` 对应到 `Nat`，或者分别翻译函数和参数，再组成 Lean 的函数应用。另一类需要调整结构，比如分类讨论、递归定义和类型层级：不能只替换名字，而要分析原来的结构，再用 Lean 支持的方式重新构造出来。


### 5.1 建立基础映射与声明映射

翻译器首先定义少量基础类型及构造器的映射，例如：
```
Rocq nat       → Lean Nat
Rocq O         → Lean Nat.zero
Rocq S         → Lean Nat.succ
Rocq eq        → Lean Eq
Rocq eq_refl   → Lean Eq.refl
```

这些映射通过 Bootstrap 检查两边的类型签名和构造器是否匹配。对于其他类型，例如 `list`、`eqType`、`ProcessorState`，翻译器通常根据 Rocq 中的声明结构生成新的 Lean 类型，而不是直接使用 Lean 中已有的类似类型。
其他 declaration 的映射则会在翻译过程中逐步建立。

### 5.2 递归翻译表达式

翻译器通过 MetaRocq 导出的 IR，识别表达式的基本结构，再递归转换成 Lean 内核表达式，而不是直接替换字符串。

例如 Rocq：

```
Definition identity (n : nat) : nat := n.
```

主要涉及：

- `nat` → `Nat`
    
- Rocq Lambda → Lean `Expr.lam`
    
- MetaRocq IR `rel 0` → Lean `Expr.bvar 0`（经过局部变量处理）
    

最后得到的 Lean 定义相当于：

```
def identity (n : Nat) : Nat := n
```

对于 theorem：

```
Theorem identity_correct :
  forall n : nat, n = n.
```

翻译器会机械生成对应的 Lean statement：

```
∀ n : Nat, n = n
```

目前采用 statement-only translation，因此原始 Rocq proof 不再机械翻译，而是交给 Lean proving agent 重新证明。

**只要表达式使用的是已经支持的结构，无论 declaration 名字是什么，都可以使用相同的规则翻译。**

### 5.3 对复杂结构进行 Lowering

有些 Rocq 结构无法直接映射到 Lean 内核表达式，需要通过特定算法重新组织成 Lean 支持的结构，这个过程称为 Lowering。

|Rocq 结构|Lean 翻译方式|
|---|---|
|`Inductive`|生成新的 Lean inductive|
|`Case`（match）|转成相应类型的 recursor|
|结构递归 `Fix`|转成 Lean recursor|
|某些 mutual `Fix`|使用联合 recursor，再投影结果|
|某些复杂递归|使用 `Acc.rec` 等机制|
|Equality proof transport|按需构造 `Eq.rec` 等证明运输|
|Universe/cumulativity 差异|通过 level 转换、约束检查和合法实例化处理|

例如 Rocq：

```
Fixpoint length (xs : list nat) : nat :=
  match xs with
  | nil => O
  | cons _ tail => S (length tail)
  end.
```

翻译器需要分析原来的递归结构，再利用翻译后列表类型的 recursor 构造对应的 Lean 函数，而不是直接把 `Fix` 替换成某个关键词。

**Lowering 的核心是保留原本的计算或证明结构，只是换成 Lean 内核能够接受的表达方式。** 并非所有复杂结构都已经支持，无法合法转换时需要报告失败。

### 5.4 按依赖顺序翻译并建立映射

假设 A 依赖 B，B 依赖 C，翻译器会按照以下顺序处理：

```
翻译 C → 检查成功 → M(C) = CL
翻译 B → 使用 M(C) → M(B) = BL
翻译 A → 使用 M(B) → M(A) = AL
```

也就是说，翻译器会按照 dependency 顺序，逐个翻译并检查 declaration，成功后将 Rocq declaration 和对应的 Lean declaration 注册到映射表中。

之后如果新的 declaration 引用了已经翻译的函数或类型，就可以直接查找映射表，引用对应的 Lean 常量，而不需要重新翻译它的定义。

这里不仅要匹配完整的 declaration 名称，还必须正确处理 universe 实例及相关类型信息，确保引用在 Lean 中仍然合法。
